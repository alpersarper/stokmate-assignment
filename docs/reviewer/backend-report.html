Backend architecture & modifications

Backend mimarisi ve değişiklikler

The backend was provided with the assignment — a .NET 8 Web API with an in-memory store. It was not authored here. This report describes how it works, and then documents in full the three modifications made during the assignment, each with its original behavior, reason, impact, and verification.

Backend ödevle birlikte verildi — in-memory bir veri deposu kullanan bir .NET 8 Web API. Burada yazılmadı. Bu rapor önce nasıl çalıştığını anlatıyor, ardından ödev sırasında yapılan üç değişikliği özgün davranışı, gerekçesi, etkisi ve doğrulamasıyla eksiksiz belgeliyor.

Overview

Genel bakış

ASP.NET Core controllers over EF Core's in-memory provider, fixed to port 5080 on all interfaces, CORS fully open, HTTP only, Swagger exposed. Everything — products, sessions, tokens — lives in process memory and is re-seeded on every start (80 products, 8 categories, 12 brands, 6 suppliers, 1 user). Error bodies are Turkish text/plain, not JSON, which shaped the clients' error handling. Verified behavior is recorded in docs/API_CONTRACT.md from a runtime battery plus a full source read — the clients were built against that record, never against assumptions.

EF Core'un in-memory sağlayıcısı üzerinde ASP.NET Core controller'ları: tüm arayüzlerde sabit 5080 portu, tamamen açık CORS, yalnızca HTTP, açık Swagger. Ürünler, oturumlar, token'lar — her şey süreç belleğinde tutulur ve her başlatmada yeniden seed'lenir (80 ürün, 8 kategori, 12 marka, 6 tedarikçi, 1 kullanıcı). Hata gövdeleri JSON değil Türkçe text/plain; bu da istemcilerin hata işleyişini biçimlendirdi. Doğrulanmış davranış, bir runtime test bataryası ve kaynak kodun baştan sona okunmasıyla docs/API_CONTRACT.md belgesine kaydedildi — istemciler varsayımlara göre değil, bu kayda göre geliştirildi.

Product lifecycle — a representative write

Ürün yaşam döngüsü — temsili bir yazma işlemi

Editing a product on web: the client reads GET /products/{id}, the user edits, and the client sends the complete object back with PUT. The service resolves the product (404 first, even before body validation), validates fields in a fixed order, checks category/brand/supplier relations, enforces SKU uniqueness (409), then writes and refreshes updatedAt, returning the full updated product. Stock uses the dedicated PATCH path instead — an absolute value, not a delta — which is what makes the mobile workflow first-class rather than a special case of product editing.

Web'de ürün düzenleme: istemci GET /products/{id} ile okur, kullanıcı düzenler ve istemci nesnenin tamamını PUT ile geri gönderir. Servis önce ürünü bulur (gövde doğrulamasından da önce 404), alanları sabit bir sırada doğrular, kategori/marka/tedarikçi ilişkilerini kontrol eder, SKU tekilliğini zorunlu kılar (409), sonra yazar ve updatedAt'i tazeler; güncellenmiş ürünün tamamını döner. Stok bunun yerine özel PATCH yolunu kullanır — delta değil, mutlak bir değer — mobil iş akışını ürün düzenlemenin özel bir hâli olmaktan çıkarıp birinci sınıf yapan da budur.

The trap the clients must respect: PUT is a true full replace — omitted fields take C# defaults rather than being preserved (proved at runtime: omitting price set it to 0, omitting barcode wiped it). Likewise an empty stock PATCH body silently sets stock to 0. Both are structurally prevented in the shared client: PUT bodies are built from a fresh detail read, and the stock endpoint only accepts a validated numeric argument.
İstemcilerin gözetmek zorunda olduğu tuzak: PUT gerçek bir full-replace'tir — gönderilmeyen alanlar korunmaz, C# varsayılan değerlerini alır (runtime'da kanıtlandı: price gönderilmeyince 0 oldu, barcode gönderilmeyince silindi). Aynı şekilde boş bir stok PATCH gövdesi stoğu sessizce 0 yapar. İkisi de shared client'ta yapısal olarak engellendi: PUT gövdeleri taze bir detay okumasından kurulur ve stok endpoint'i yalnızca doğrulanmış sayısal bir argüman kabul eder.

Modifications made during the assignment

Ödev sırasında yapılan değişiklikler

The assignment asks to avoid backend changes; these three were each judged necessary, kept minimal, follow existing backend patterns and error conventions, and are documented in the contract and decision records.

Ödev, backend değişikliklerinden kaçınılmasını istiyor; bu üç değişikliğin her biri gerekli görüldü, asgari düzeyde tutuldu, mevcut backend desenlerini ve hata kurallarını izliyor ve API kontratı ile karar kayıtlarında belgelendi.

a6b54761. Added GET /products/{id}1. GET /products/{id} eklendi

Original behavior
No product-by-id read existed. The route returned 405; product data was only obtainable through the paged list, whose DTO omits costPrice, supplierId, and description.
Modification
One read-only controller action, one DTO, one service method: returns the 16 list fields plus those three.
Reason
The assignment mandates product-detail screens fed by the actual API and web edits persisted through it. But the only whole-product write is a full-replace PUT requiring exactly those three fields — so any legal client PUT silently overwrote real data. This was proved at runtime during discovery, not theorized. Alternatives considered and rejected: guessing the three values from cached list rows (silent data corruption); widening the list DTO (changes an existing contract for every consumer and still gives no per-id fetch for deep links); relaxing PUT to partial-update semantics (a behavioral change to an existing write path — strictly more invasive).
Impact
Detail screens on both clients read real API data, and product edits round-trip losslessly. Observable side effect: the route no longer 405s, and the Allow header on a 405 for that path now lists GET.
Compatibility
Purely additive and read-only. No existing endpoint's behavior changed; the list DTO is still exactly 16 fields; /products/stats route precedence is intact.
Verification
Runtime: 200 happy path; 404 for an unknown id using the existing Turkish plain-text convention; 401 without/with an invalid bearer; regression checks on the list DTO and stats route; and a lossless GET→PUT round-trip proving costPrice, supplierId, description, barcode, isFeatured all survive an edit.
Özgün davranış
Id ile ürün okuma yoktu. Rota 405 dönüyordu; ürün verisine yalnızca sayfalı liste üzerinden ulaşılabiliyordu ve o DTO costPrice, supplierId ve description alanlarını içermiyor.
Değişiklik
Salt okunur tek bir controller action'ı, tek bir DTO, tek bir servis metodu: 16 liste alanına ek olarak bu üç alanı döner.
Gerekçe
Ödev, gerçek API'den beslenen ürün detay ekranlarını ve web düzenlemelerinin API üzerinden kalıcı olmasını zorunlu kılıyor. Ancak ürünün tamamını yazan tek yol, tam da bu üç alanı zorunlu tutan full-replace PUT — dolayısıyla kurallara uygun herhangi bir istemci PUT'u gerçek veriyi sessizce eziyordu. Bu, keşif sırasında runtime'da kanıtlandı; teorik bir çıkarım değil. Değerlendirilip elenen alternatifler: üç değeri cache'teki liste satırlarından tahmin etmek (sessiz veri bozulması); liste DTO'sunu genişletmek (mevcut kontratı tüm tüketiciler için değiştirir ve deep link'ler için yine id bazlı okuma sağlamaz); PUT'u kısmi güncelleme semantiğine gevşetmek (mevcut bir yazma yolunun davranışını değiştirir — açıkça daha müdahaleci).
Etki
Her iki istemcideki detay ekranları gerçek API verisini okur ve ürün düzenlemeleri kayıpsız gidip gelir. Gözlemlenebilir yan etki: rota artık 405 dönmüyor ve bu yol için 405'te dönen Allow başlığı artık GET'i de listeliyor.
Uyumluluk
Tamamen ekleyici ve salt okunur. Mevcut hiçbir endpoint'in davranışı değişmedi; liste DTO'su hâlâ tam 16 alan; /products/stats rota önceliği bozulmadı.
Doğrulama
Runtime: happy path'te 200; bilinmeyen id için mevcut Türkçe düz metin konvansiyonuyla 404; bearer olmadan ve geçersiz bearer ile 401; liste DTO'su ve stats route'u üzerinde regresyon kontrolleri; ve costPrice, supplierId, description, barcode, isFeatured alanlarının düzenleme sonrasında korunduğunu gösteren kayıpsız GET→PUT turu.

faf1a852. Stock updates rejected for Discontinued products (409)2. Discontinued ürünlerde stok güncellemeleri reddediliyor (409)

Original behavior
PATCH /products/{id}/stock accepted updates regardless of product status.
Modification
An eight-line guard in ProductService: status 3 (Üretim Durduruldu) throws the existing ConflictException → 409 text/plain "Üretimi durdurulmuş ürünün stoğu güncellenemez." Stock and updatedAt are left untouched.
Reason
An explicit product assumption, documented as such: a store terminal could otherwise keep booking stock onto a product head office has already discontinued. Enforcing it in the backend — not merely disabling a button — is what protects stale clients: a device that opened the product while it was Active gets a definitive rejection if it saves afterwards.
Impact
Mobile disables the stock editor for Discontinued products, maps the 409 to a specific localized message, and refetches the detail so the screen flips into the locked state. Status 1 (Active) and 2 (Passive) are unchanged — Passive deliberately still accepts stock, because the assignment defines no restriction for it and delisted products still receive deliveries.
Compatibility
Uses the existing 409 + Turkish plain-text convention. PUT is deliberately not restricted, so status stays editable and Discontinued remains reversible — after switching back to Active, stock updates work again.
Verification
Runtime curl battery plus a shared live-contract test: Active → 200, Passive → 200, Discontinued → 409 with stock confirmed unchanged by read-back, unknown id → 404, auth behavior unchanged.
Özgün davranış
PATCH /products/{id}/stock, ürün durumundan bağımsız olarak güncellemeleri kabul ediyordu.
Değişiklik
ProductService içinde sekiz satırlık bir kontrol: durum 3 (Üretim Durduruldu) mevcut ConflictException'ı fırlatır → 409 text/plain "Üretimi durdurulmuş ürünün stoğu güncellenemez." Stok ve updatedAt olduğu gibi kalır.
Gerekçe
Açıkça belirtilmiş ve öyle belgelenmiş bir ürün varsayımı: aksi hâlde bir mağaza terminali, merkezin çoktan üretimini durdurduğu bir ürüne stok işlemeye devam edebilirdi. Bunu yalnızca bir butonu devre dışı bırakarak değil backend'de zorunlu kılmak, stale istemcileri koruyan şeydir: ürünü Active hâldeyken açmış bir cihaz, sonradan kaydetmeye kalkarsa kesin bir ret alır.
Etki
Mobil, Discontinued ürünlerde stok editörünü devre dışı bırakır, 409'u duruma özel ve yerelleştirilmiş bir mesaja eşler ve detayı yeniden çekerek ekranı kilitli duruma geçirir. Durum 1 (Active) ve 2 (Passive) değişmedi — Passive bilinçli olarak stok kabul etmeye devam ediyor; çünkü ödev bunun için bir kısıt tanımlamıyor ve satıştan kaldırılmış ürünlere sevkiyat gelmeye devam eder.
Uyumluluk
Mevcut 409 + Türkçe düz metin konvansiyonunu kullanır. PUT bilinçli olarak kısıtlanmadı; böylece status düzenlenebilir kalır ve Discontinued geri alınabilir — tekrar Active'e geçildiğinde stok güncellemeleri yeniden çalışır.
Doğrulama
Runtime curl bataryası ve shared paketindeki canlı kontrat testi: Active → 200, Passive → 200, Discontinued → 409 ve geri okumayla stoğun değişmediği doğrulandı, bilinmeyen id → 404, auth davranışı değişmedi.

e1ff1b03. Rate limiting on product reads3. Ürün okumalarında rate limiting

Original behavior
No throttling of any kind.
Modification
The named product-reads policy applied to GET /products, GET /products/{id}, and GET /products/stats: fixed window, 60 requests per 10 seconds, partitioned by the Authorization header (falling back to client IP), no queueing. Over the limit → 429 with the project's Turkish plain-text body and a Retry-After header.
Reason
The freshness feature adds polling, pull-to-refresh, and manual refresh. Client-side cooldowns are a UX affordance, not a boundary — a server-side limit is the independent one. Partitioning per token means one client's misbehavior cannot consume another session's budget.
Impact
None in normal operation: the limit is deliberately generous, and legitimate behavior (15 s list poll, 10 s detail poll, cooldown-gated manual refreshes, pagination bursts) stays far below it. Auth, lookups, and every write endpoint are unlimited. Both clients treat 429 as a 4xx and never auto-retry it.
Compatibility
Additive middleware on read paths only; response shapes for successful reads are unchanged.
Verification
Runtime: 30 sequential reads at 2 req/s → all 200; a tight loop of 100 → exactly the first 60 succeed, the rest 429; a second session's token unaffected while the first is limited; lookups, /auth/me, and stock PATCH still 200 during a limited window; the token succeeds again after the window passes.
Özgün davranış
Hiçbir türden sınırlama yoktu.
Değişiklik
GET /products, GET /products/{id} ve GET /products/stats üzerine uygulanan product-reads adlı politika: sabit pencere, 10 saniyede 60 istek, Authorization başlığına göre bölümlenmiş (yoksa istemci IP'sine düşer), kuyruk yok. Limit aşılınca → projenin Türkçe düz metin gövdesi ve Retry-After başlığıyla 429.
Gerekçe
Tazelik özelliği polling, pull-to-refresh ve manuel yenileme getiriyor. İstemci tarafındaki cooldown'lar bir UX kolaylığıdır, gerçek bir sınır değil — bağımsız sınır sunucu tarafındakidir. Token başına partitioning sayesinde bir istemcinin hatalı davranışı başka bir oturumun bütçesini tüketemez.
Etki
Normal kullanımda yok: limit bilinçli olarak cömert tutuldu ve meşru davranış (15 saniyelik liste polling'i, 10 saniyelik detay polling'i, cooldown'la sınırlanan manuel yenilemeler, pagination burst'leri) bunun çok altında kalıyor. Auth, lookup'lar ve tüm yazma endpoint'leri sınırsız. Her iki istemci de 429'u bir 4xx olarak ele alır ve asla otomatik retry yapmaz.
Uyumluluk
Yalnızca okuma yollarına eklenen bir middleware; başarılı okumaların yanıt şekilleri değişmedi.
Doğrulama
Runtime: saniyede 2 istekle 30 ardışık okuma → hepsi 200; 100 isteklik sıkı bir döngü → tam olarak ilk 60'ı başarılı, kalanı 429; ilki sınırlıyken ikinci bir oturumun token'ı etkilenmiyor; sınırlı pencere boyunca lookup'lar, /auth/me ve stok PATCH hâlâ 200; pencere geçtikten sonra token yeniden başarılı oluyor.

What was deliberately preserved

Bilinçli olarak korunanlar

  • The full-replace PUT semantics — relaxing them to partial updates would have been convenient for the client but is a behavioral change to an existing write path; the client adapted instead.
  • Turkish plain-text error bodies — not "improved" into structured JSON. The clients normalize them once, in the shared client, and identify known failures by status code plus request context rather than by matching prose.
  • No concurrency mechanism was invented — no versions, ETags, or preconditions were bolted on. Writes remain last-write-wins, which is documented rather than hidden behind fake client-side protection.
  • Seeding, ordering, collation, pagination clamps, and every response shape — untouched, including quirks like host-locale-dependent Turkish letter folding, which is documented as server-defined and never re-filtered client-side.
  • Unused endpoints (create, delete, suppliers) — left in place, not consumed.
  • Full-replace PUT semantiği — kısmi güncellemeye gevşetmek istemci için kolaylık olurdu ama mevcut bir yazma yolunun davranışını değiştirmek demekti; bunun yerine istemci uyum sağladı.
  • Türkçe düz metin hata gövdeleri — yapılandırılmış JSON'a "iyileştirilmedi". İstemciler bunları shared client'ta bir kez normalize eder ve bilinen hataları metin eşleştirerek değil, status kodu ve istek bağlamıyla tanır.
  • Concurrency mekanizması uydurulmadı — versiyon alanı, ETag ya da precondition eklenmedi. Yazmalar last-write-wins olarak kaldı; bu sınır, sahte bir istemci tarafı korumasının arkasına saklanmak yerine belgelendi.
  • Seed verisi, sıralama, collation, pagination sınırları ve tüm yanıt şekilleri — hiçbirine dokunulmadı; sunucunun locale'ine bağlı Türkçe i/ı harf davranışı gibi tuhaflıklar dâhil. Bu davranış sunucu tanımlı olarak belgelendi ve istemcide asla yeniden filtrelenmedi.
  • Kullanılmayan endpoint'ler (create, delete, suppliers) — yerinde bırakıldı, tüketilmedi.

Production considerations

Üretim ortamı için değerlendirmeler

These are scope boundaries of a take-home exercise, not defects in the provided backend:

Bunlar bir take-home projesinin kapsam sınırlarıdır; verilen backend'in kusurları değil:

  • Persistence — the in-memory store re-seeds on every restart and wipes all sessions; a real deployment needs a database and durable session storage.
  • Distributed rate limiting — the current limiter is per-process, which is correct for a single local instance but would need shared state behind a load balancer.
  • Transport and secrets — HTTP only with open CORS and no secret management; production would mean HTTPS (the clients need only an environment-variable change), scoped CORS, and managed credentials.
  • Concurrency — a version or ETag mechanism would let clients detect stale writes instead of accepting last-write-wins.
  • Observability — structured logging, metrics, and tracing are absent, as expected at this scale.
  • Kalıcılık — in-memory depo her yeniden başlatmada baştan seed'lenir ve tüm oturumları siler; gerçek bir deployment için veritabanı ve kalıcı oturum saklama gerekir.
  • Dağıtık rate limiting — mevcut limiter süreç bazlıdır; tek bir yerel instance için doğru ama bir load balancer arkasında paylaşılan state gerektirir.
  • Transport ve gizli bilgiler — açık CORS ile yalnızca HTTP; secret yönetimi yok. Üretimde HTTPS (istemciler için tek gereken bir ortam değişkeni değişikliği), kapsamı daraltılmış CORS ve yönetilen kimlik bilgileri olurdu.
  • Concurrency — bir versiyon ya da ETag mekanizması, last-write-wins davranışını kabullenmek yerine istemcilerin stale veriye dayanan yazmaları fark etmesini sağlardı.
  • Gözlemlenebilirlik — yapılandırılmış loglama, metrikler ve tracing yok; bu ölçekte beklendiği gibi.
