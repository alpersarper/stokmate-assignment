Web admin architecture

Web yönetim paneli mimarisi

The head-office operational surface: product management over the live API — search, filter, sort, paginate, inspect, and edit. Source: web/. Vite + React + TypeScript (strict), React Router, TanStack Query v5, Tailwind CSS v4 + shadcn/ui.

Merkez ofisin operasyonel yüzeyi: canlı API üzerinden ürün yönetimi — arama, filtreleme, sıralama, sayfalama, inceleme ve düzenleme. Kaynak: web/. Vite + React + TypeScript (strict), React Router, TanStack Query v5, Tailwind CSS v4 + shadcn/ui.

Purpose

Amaç

The web app is the admin half of the product: head-office staff manage the catalog. Its job is operational efficiency — many products visible at once, fast narrowing, safe edits, and confidence that what is on screen matches the server. It is deliberately not a consumer-styled site; density and scanability win over presentation.

Web uygulaması ürünün yönetim tarafı: kataloğu merkez ofis ekibi yönetir. İşi operasyonel verimlilik — aynı anda çok sayıda ürünün görünmesi, hızlı daraltma, güvenli düzenleme ve ekrandakinin sunucudakiyle eşleştiğine dair güven. Bilinçli olarak tüketiciye yönelik bir site değil; yoğunluk ve göz taranabilirliği görsel sunumun önünde geliyor.

Architecture

Mimari

A three-route SPA (/login, /products, /products/:id) in a feature-folder-lite layout: api/ (client instance + storage adapter), auth/, products/, components/ (shadcn primitives + freshness control), lib/ (query client, refresh pipeline, currency input), i18n/. All server communication goes through the shared @stokmate/shared client; components never call fetch.

Üç rotalı bir SPA (/login, /products, /products/:id), hafif bir feature-folder düzeninde: api/ (client örneği + storage adaptörü), auth/, products/, components/ (shadcn primitifleri + tazelik kontrolü), lib/ (query client, yenileme hattı, para girişi), i18n/. Tüm sunucu iletişimi paylaşılan @stokmate/shared client'ı üzerinden geçer; bileşenler asla fetch çağırmaz.

Representative data flow: saving a product edit

Örnek veri akışı: ürün düzenlemesini kaydetme

Why the full body matters: the API's PUT is a verified full replace — any omitted field is silently reset to its C# default. The form therefore always initializes from a fresh GET /products/{id} and sends the complete object back. A shared unit test asserts that barcode/isFeatured/costPrice/description survive an edit.
Tam gövde neden önemli: API'nin PUT'u doğrulanmış şekilde tam değiştirme yapıyor — gönderilmeyen her alan sessizce C# varsayılanına dönüyor. Bu yüzden form her zaman taze bir GET /products/{id} ile başlar ve nesnenin tamamını geri gönderir. Paylaşılan bir unit test, barcode/isFeatured/costPrice/description alanlarının bir düzenlemeden sağ çıktığını doğrular.

Product list

Ürün listesi

  • Search — 300 ms debounce, trimmed, sent as q (server-side substring match on name/SKU/barcode); input preserved on failure; clearing restores the default list.
  • Filters — category, brand, and status selects (single-value, matching the API's capability); any change resets to page 1; active filters stay visible with a reset action.
  • Sorting — clickable Name/Price/Stock/Updated headers cycle asc/desc, mapped to the API's sort/dir params; server-side, like everything else about the list.
  • Pagination — 1-based pages; totalPages computed client-side (ceil(total/pageSize)) because the API sends only total.
  • Freshness & refresh — "Updated just now / X ago" from dataUpdatedAt; a manual Refresh button with a 4 s post-settle cooldown; while the page is visible/focused, a poll anchored to the last fetch settle requests the exact current dataset (q, category, brand, status, sort, direction, page, page size) about every 15 s. It stops while hidden and visibility restoration triggers targeted revalidation without stacking.
  • States — table skeleton on first load; keepPreviousData + a subtle fetching indicator during narrowing (existing rows stay visible); dedicated zero-result and error+retry states; count label with correct EN pluralization.
  • Domain presentation — status as localized text badges (color as reinforcement only), stock with the API's own low-stock signal (stock ≤ minStock) in amber and out-of-stock in red, prices in tabular numerals via integer-kuruş formatting.
  • Arama — 300 ms debounce, baştaki/sondaki boşluklar kırpılır, q olarak gönderilir (sunucu tarafında ad/SKU/barkod üzerinde alt dize eşleşmesi); hata durumunda girilen metin korunur; temizlemek varsayılan listeyi geri getirir.
  • Filtreler — kategori, marka ve durum seçimleri (API'nin desteklediği gibi tek değerli); herhangi bir değişiklik sayfa 1'e döner; aktif filtreler bir sıfırlama eylemiyle birlikte görünür kalır.
  • Sıralama — tıklanabilir Ad/Fiyat/Stok/Güncellenme başlıkları asc/desc arasında döner, API'nin sort/dir param'larına eşlenir; listeyle ilgili her şey gibi sunucu tarafında.
  • Sayfalama — sayfa numaraları 1'den başlar; API yalnızca total gönderdiği için totalPages istemci tarafında hesaplanır (ceil(total/pageSize)).
  • Tazelik ve yenileme — dataUpdatedAt üzerinden "az önce / X önce güncellendi"; istek tamamlandıktan sonra 4 s bekleme süresi olan manuel bir Yenile butonu; sayfa görünür/odaktayken son isteğin tamamlanmasına çıpalanan polling yaklaşık her 15 sn'de açık veri kümesinin tam parametrelerini (q, kategori, marka, durum, sıralama, yön, sayfa, sayfa boyutu) ister. Gizliyken durur; görünürlük geri geldiğinde üst üste binmeden hedefli revalidation yapar.
  • Durumlar — ilk yüklemede tablo skeleton'ı; daraltma sırasında keepPreviousData + hafif bir yükleniyor göstergesi (mevcut satırlar görünür kalır); sonuç yok ve hata+tekrar dene için ayrı durumlar; İngilizcede doğru çoğullanan sayı etiketi.
  • Alan gösterimi — durum, yerelleştirilmiş metin rozetleriyle (renk yalnızca destekleyici), stok, API'nin kendi düşük stok sinyaliyle (stock ≤ minStock) amber ve tükendiğinde kırmızı, fiyatlar tam sayı kuruş biçimlendirmesiyle tablo rakamlarında.

Product edit flow

Ürün düzenleme akışı

  1. Detail opens read-only; editing is an explicit action (UX-002).
  2. The form initializes from a fresh detail read; prices are edited in ₺ and converted exactly to integer kuruş (no floats anywhere).
  3. The form edits and validates name, price, stock, and status. Required non-editable PUT fields (SKU, unit, supplier, cost price, description, and the remaining detail fields) are round-tripped unchanged from the fresh detail read; the backend stays authoritative.
  4. Save is enabled only when dirty ∧ valid ∧ not submitting. Cancel, back navigation, and logout are all guarded by an unsaved-changes confirmation (useBlocker).
  5. On success: exit edit mode, show the persisted server state, toast. On failure: stay in edit mode, preserve input, surface the error (known statuses map to localized messages — e.g. the SKU-conflict 409; unknown ones get a generic fallback with the server text as detail).
  1. Detay salt okunur açılır; düzenleme açık bir eylemdir (UX-002).
  2. Form taze bir detay okumasıyla başlar; fiyatlar ₺ olarak düzenlenir ve tam olarak tam sayı kuruşa çevrilir (hiçbir yerde float yok).
  3. Form ad, fiyat, stok ve durumu düzenleyip doğrular. Düzenlenemeyen zorunlu PUT alanları (SKU, birim, tedarikçi, maliyet fiyatı, açıklama ve kalan detay alanları) taze detay okumasından değişmeden aktarılır; nihai otorite backend'de kalır.
  4. Kaydet yalnızca değişmiş ∧ geçerli ∧ gönderim sürmüyor durumunda aktiftir. İptal, geri gitme ve çıkış yapma; hepsi kaydedilmemiş değişiklikler onayıyla korunur (useBlocker).
  5. Başarıda: düzenleme modundan çık, kalıcılaşmış sunucu state'ini göster, toast. Başarısızlıkta: düzenleme modunda kal, girilenleri koru, hatayı göster (bilinen durum kodları yerelleştirilmiş mesajlara eşlenir — örneğin SKU çakışmasındaki 409; bilinmeyenler için sunucu metni detay olarak verilen genel bir mesaj gösterilir).

Auth & session lifecycle

Kimlik doğrulama ve oturum yaşam döngüsü

  1. Login — RHF form; "Remember me" decides the token store: localStorage (survives the browser) vs sessionStorage (dies with the tab). Tokens are opaque; nothing is decoded client-side.
  2. Startup restore — if a persisted session exists, AuthProvider validates it once via GET /auth/me before rendering the app (StrictMode-deduped), showing a restoring state instead of a login flash.
  3. Mid-session expiry — any 401 triggers the shared client's single-flight refresh; concurrent 401s join one refresh call (strict rotation makes racing fatal); the original request retries once with the new token. Users never see a 15-minute-token hiccup.
  4. Unrecoverable session — refresh fails (rotated away, revoked, or the in-memory backend restarted): storage is cleared and the app returns to login cleanly. A session epoch counter ensures stale in-flight requests can neither resurrect a logged-out session nor tear down a new one.
  5. Logout — best-effort server revoke, always clear local state, navigate to login with history replaced. The backend drops all of the user's access tokens across clients — which is exactly the scenario the refresh interceptor exists for on the other client.
  1. Giriş — RHF formu; "Beni hatırla" token'ların nerede saklanacağını belirler: localStorage (tarayıcı kapansa da kalır) ya da sessionStorage (sekmeyle birlikte gider). Token'lar opak; istemci tarafında hiçbir şey çözümlenmez.
  2. Açılışta oturum geri yükleme — saklanmış bir oturum varsa AuthProvider, uygulamayı render etmeden önce onu GET /auth/me ile bir kez doğrular (StrictMode'da tekrarı engellenir) ve giriş ekranının bir an parlaması yerine geri yükleniyor durumunu gösterir.
  3. Oturum ortasında sürenin dolması — herhangi bir 401, paylaşılan client'ın single-flight refresh'ini tetikler; eşzamanlı 401'ler tek bir refresh çağrısına katılır (katı rotasyon nedeniyle yarışmak ölümcül olur); asıl istek yeni token'la bir kez tekrarlanır. Kullanıcı 15 dakikalık token'ın takılmasını hiç görmez.
  4. Kurtarılamayan oturum — refresh başarısız olursa (rotasyonla geçersizleşmiş, iptal edilmiş ya da in-memory backend yeniden başlamış): depolama temizlenir ve uygulama temiz biçimde girişe döner. Bir oturum epoch sayacı sayesinde uçuştaki bayat istekler ne kapanmış bir oturumu diriltebilir ne de yeni bir oturumu düşürebilir.
  5. Çıkış — sunucuda best-effort iptal, yerel state her hâlde temizlenir, geçmiş değiştirilerek girişe yönlendirilir. Backend kullanıcının tüm istemcilerdeki access token'larını düşürür — ki diğer istemcideki refresh interceptor'ı tam da bu senaryo için var.

Admin UX philosophy

Yönetim paneli UX yaklaşımı

Operational software for daily use: a dense, scannable table as the centerpiece; status as text labels with color as reinforcement only; tabular numerals for every quantity; restrained neutral palette with one chromatic accent; no decoration, gradients, or hero moments. Loading feedback is layered so work is never interrupted — skeletons only on first load, previous data during narrowing, subtle indicators during background refresh. The design language is recorded in web/DESIGN.md and the shared DESIGN.md.

Günlük kullanım için operasyonel yazılım: merkezde yoğun, göz taranabilir bir tablo; durum metin etiketleriyle, renk yalnızca destekleyici; her sayı için tablo rakamları; tek bir renkli vurgu taşıyan ölçülü nötr palet; süsleme, gradient ya da hero alanı yok. Yükleme geri bildirimi katmanlı, böylece iş asla kesilmez — skeleton yalnızca ilk yüklemede, daraltma sırasında önceki veri, arka plan yenilemesinde hafif göstergeler. Tasarım dili web/DESIGN.md ve paylaşılan DESIGN.md içinde kayıtlı.

Trade-offs and limitations

Ödünleşimler ve sınırlar

  • Last-write-wins editing — the API has no concurrency mechanism (verified), so simultaneous edits overwrite; mitigated by fresh-read initialization and post-save re-sync, and documented rather than papered over with fake client-side "protection".
  • Token storage in web storage — localStorage carries the usual XSS caveat; an httpOnly-cookie scheme would require backend changes out of proportion for this assignment.
  • Polling, not realtime — the cross-client bonus converges within ~15 s; a push channel was deliberately rejected (see decisions).
  • Single main JS chunk > 500 kB — Vite's informational warning; code-splitting three routes wasn't worth the complexity here.
  • Son yazan kazanır — API'de eşzamanlılık mekanizması yok (doğrulandı), dolayısıyla aynı anda yapılan düzenlemeler birbirinin üzerine yazar; taze okumayla başlatma ve kayıt sonrası yeniden senkronizasyon bunu hafifletir, üstelik sahte bir istemci tarafı "koruma" ile örtmek yerine belgelendi.
  • Token'ların web storage'da tutulması — localStorage bilindik XSS uyarısını taşır; httpOnly cookie düzeni, bu ödev için orantısız kalacak backend değişiklikleri gerektirirdi.
  • Realtime değil, polling — istemciler arası bonus ~15 s içinde yakınsar; push kanalı bilinçli olarak elendi (bkz. kararlar).
  • Tek ana JS chunk'ı > 500 kB — Vite'ın bilgilendirme amaçlı uyarısı; üç rotayı code-splitting ile ayırmak buradaki karmaşıklığa değmezdi.
