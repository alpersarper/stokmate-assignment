StokMate · Reviewer report

Mobile architecture

The store-floor application: a productized, customer-facing app whose primary job is updating stock quickly and safely. Source: mobile/. Expo (managed) + React Native + TypeScript, React Navigation native stack, TanStack Query v5, hand-styled UI. Delivered as a verified release APK.

Product purpose

This is not a shrunken admin panel. Store staff hold a phone one-handed, find a product, and correct its stock — so the app is built around discovery and a single confident write. Products are presented as a browsable catalog (image, name, brand, price, stock state), and the detail screen makes the current stock and the editor the visual centre of gravity. The web admin's density conventions were deliberately not carried over; what is shared is the data language (status semantics, ₺ formatting, low-stock rules), not the styling.

Data lifecycle

Launch → session → first screen

  1. App starts in status: 'restoring' and reads any persisted token pair from secure storage.
  2. If a pair exists it is validated with GET /auth/me. Success → signedIn; a dead session (e.g. the in-memory backend restarted) → signedOut silently, with no error spam on a screen the user never saw.
  3. The list screen mounts and fetches page 1 of the default dataset (Active products, name ascending).
  4. Scrolling appends pages; changing search/filters/sort creates a new dataset under a new key, with the previous results kept on screen until the new ones arrive.

Mutation → cache

A stock save returns the full updated product — canonical persisted server state. Instead of invalidating and refetching every loaded page (which on an infinite list means a request storm), the response is applied directly to the caches: the detail entry is patched (preserving detail-only fields) and the matching row is patched inside every cached list dataset. Dataset membership — a product that no longer matches an active filter — is deliberately not corrected in place; that resolves on the next explicit refresh of that dataset, which keeps rows from vanishing under the user's thumb mid-interaction.

Product list

  • Discovery-oriented rows — image, name, brand, price, and a stat rail carrying the stock state (with "Low stock"/"Out of stock" text labels, not colour alone).
  • Search — 300 ms debounce, trimmed, server-side (q); the same substring match the web admin uses.
  • Filters & sort — bottom sheets for status/category/brand and an 8-option sort menu, all mapped to the API's own parameters; lookup lists load lazily the first time the filter sheet opens. Active filter chips carry their own labels, so they never depend on the lookup cache.
  • Pagination — infinite scroll armed by a genuine user gesture: one fetchNextPage per drag/fling, so momentum can't chain-load pages; failures pause pagination behind an explicit footer Retry; the backend-reported total decides when the list ends ("You've reached the end").
  • Result count comes from the backend's total for the filtered dataset — never the number of loaded rows.
  • Refresh — pull-to-refresh and the explicit Refresh action share one protected pipeline; the freshness indicator shows the age of the visible data.
  • States — skeleton rows on first load, previous results retained while a new dataset loads, dedicated empty/zero-result and error+retry states.

Product detail & the stock workflow

The detail screen leads with a hero card (image, name, brand, price, status) and puts current stock immediately beside the editor — the one raised surface on the screen. Supporting information (SKU, barcode, category, supplier description, min-stock) sits below, deliberately secondary.

Discontinued products are stock-locked. The editor disables its controls and shows a localized notice — but the real protection is server-side: the backend rejects the update with 409. A device that opened the product while it was Active and saves after head office discontinued it gets a definitive rejection, a specific message, and a detail refetch that flips the screen into the locked presentation. See the backend report.

Networking

  • One variable: EXPO_PUBLIC_API_URL. Unset, it resolves to http://10.0.2.2:5080 on Android (the emulator's alias for the host machine — Android localhost is the device itself) and http://localhost:5080 elsewhere.
  • Physical devices and APKs set it explicitly to the host's LAN address; a hosted deployment would set an HTTPS URL through the same variable with no code change. There is deliberately no in-app server-settings screen.
  • Release builds bake the value in at JS-bundling time, which is why the delivered APK targets the emulator host and retargeting means a rebuild (documented in the README).
  • Cleartext HTTP is enabled via expo-build-properties only because the provided backend is HTTP-only; without it every network call in a release build fails.
  • Development uses a native debug build with Metro; expo-dev-client is a dev-build dependency and was verified inert in the release artifact (no dev-launcher activity, zero dev-menu entries). Debugging tooling is not part of the app's architecture.

Localization

English (default) and Turkish, switchable at runtime and persisted, via a small typed message catalog — the same approach as web. Chrome, states, validation, and status labels are localized; API data (product, brand, category names) never is. Backend error prose is never string-matched: failures are identified by status code plus request context and mapped to localized messages, with a generic localized fallback otherwise. Prices are always TRY, formatted from integer kuruş with locale-aware separators (₺39,50 tr / ₺39.50 en) and an explicit ₺ prefix, because Hermes renders the currency code instead of the symbol.

Why Expo (managed)

The assignment leaves Expo vs bare React Native open. Managed Expo keeps native configuration declarative — the cleartext-HTTP flag, icons, and build properties are config, not patched Gradle files — while expo prebuild produces a full native project on demand, so the APK is built locally with plain Gradle and no cloud account or build queue. Rationale, alternatives, and the signing caveat: engineering decisions.

Mobile UI philosophy

Surface hierarchy instead of outlines: a stone ground, borderless white content cards with faint elevation, filled (not bordered) controls, and exactly one raised surface per screen — the stock editor, because that is the screen's job. One brand-ish blue reserved for primary actions; semantic colours (danger/warning/success) carry the same meanings as the web admin's and are never repurposed for emphasis. Every stock numeral uses tabular figures. Snackbars are queued and bottom-anchored; sheets keep their actions above the gesture nav bar. The full token set and conventions are recorded in mobile/DESIGN.md.

Trade-offs and limitations

  • Hand-styled UI costs more styling effort than a component kit, accepted to keep the dependency set minimal — the hardest piece (queued snackbars) would have needed custom code anyway.
  • Fixed API target in the APK — by design (configuration over UI surface); retargeting is a documented rebuild.
  • Debug-keystore signing — assignment-grade, not a store-ready signature.
  • Last-write-wins for stock, except the Discontinued rule; the app surfaces "changed elsewhere" rather than pretending to prevent it.
  • Product images require internet (the seed data points at a public placeholder service); failures degrade gracefully so they don't read as app failures.
  • Android-verified only — the assignment asks for an Android APK; iOS is unbuilt though the code paths exist.
