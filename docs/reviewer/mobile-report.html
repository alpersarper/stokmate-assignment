StokMate · Değerlendirici raporu

Mobile architecture

Mobil mimari

The store-floor application: a productized, customer-facing app whose primary job is updating stock quickly and safely. Source: mobile/. Expo (managed) + React Native + TypeScript, React Navigation native stack, TanStack Query v5, hand-styled UI. Delivered as a verified release APK.

Mağaza sahasının uygulaması: birincil işi stok güncellemeyi hızlı ve güvenli yapmak olan, müşteri uygulaması kalitesinde ürünleşmiş bir uygulama. Kaynak: mobile/. Expo (managed) + React Native + TypeScript, React Navigation native stack, TanStack Query v5, elle tasarlanmış UI. Doğrulanmış bir release APK'sı olarak teslim edildi.

Product purpose

Ürünün amacı

This is not a shrunken admin panel. Store staff hold a phone one-handed, find a product, and correct its stock — so the app is built around discovery and a single confident write. Products are presented as a browsable catalog (image, name, brand, price, stock state), and the detail screen makes the current stock and the editor the visual centre of gravity. The web admin's density conventions were deliberately not carried over; what is shared is the data language (status semantics, ₺ formatting, low-stock rules), not the styling.

Bu, küçültülmüş bir admin paneli değil. Mağaza personeli telefonu tek eliyle tutar, bir ürünü bulur ve stoğunu düzeltir — bu yüzden uygulama, keşif ve tek bir güvenli yazma işlemi etrafında kuruldu. Ürünler göz atılabilir bir katalog olarak sunulur (görsel, ad, marka, fiyat, stok durumu); detay ekranında ise görsel ağırlık merkezi mevcut stok ile editördür. Web admin'in yoğunluk alışkanlıkları bilinçli olarak taşınmadı; paylaşılan şey stil değil, veri dilidir (durum semantiği, ₺ formatı, düşük stok kuralları).

Data lifecycle

Verinin yaşam döngüsü

Launch → session → first screen

Açılış → oturum → ilk ekran

  1. App starts in status: 'restoring' and reads any persisted token pair from secure storage.
  2. If a pair exists it is validated with GET /auth/me. Success → signedIn; a dead session (e.g. the in-memory backend restarted) → signedOut silently, with no error spam on a screen the user never saw.
  3. The list screen mounts and fetches page 1 of the default dataset (Active products, name ascending).
  4. Scrolling appends pages; changing search/filters/sort creates a new dataset under a new key, with the previous results kept on screen until the new ones arrive.
  1. Uygulama status: 'restoring' ile açılır ve secure storage'daki token çiftini okur.
  2. Çift varsa GET /auth/me ile doğrulanır. Başarılıysa → signedIn; oturum ölmüşse (ör. in-memory backend yeniden başlamıştır) → sessizce signedOut — kullanıcının hiç görmediği bir ekran için hata mesajı basılmaz.
  3. Liste ekranı mount olur ve varsayılan veri kümesinin 1. sayfasını çeker (Active ürünler, ada göre artan).
  4. Kaydırdıkça yeni sayfalar eklenir; arama/filtre/sıralama değişince yeni bir key altında yeni bir veri kümesi başlar ve yenisi gelene kadar önceki sonuçlar ekranda kalır.

Mutation → cache

Mutation → cache

A stock save returns the full updated product — canonical persisted server state. Instead of invalidating and refetching every loaded page (which on an infinite list means a request storm), the response is applied directly to the caches: the detail entry is patched (preserving detail-only fields) and the matching row is patched inside every cached list dataset. No success-path GET follows. This keeps values current, but a dataset sorted by stock or updated time is not re-sorted or re-paged locally; its order can remain stale until an explicit refresh.

Stok kaydı, güncellenen ürünün tamamını döndürür — sunucuda kalıcı hâle gelmiş kanonik state. Yüklü her sayfayı invalidate edip yeniden çekmek yerine (infinite bir listede bu bir istek fırtınası demek), yanıt doğrudan cache'lere uygulanır: detay kaydı yamalanır (yalnızca detayda bulunan alanlar korunarak) ve eşleşen satır, cache'teki her liste veri kümesinde güncellenir. Başarı yolunda ek bir GET atılmaz. Bu, değerleri güncel tutar; ancak stoğa veya güncelleme zamanına göre sıralanan bir veri kümesi yerelde yeniden sıralanıp sayfalanmaz — açık bir yenilemeye kadar sırası stale kalabilir.

Product list

Ürün listesi

  • Discovery-oriented rows — image, name, brand, price, and a stat rail carrying the stock state (with "Low stock"/"Out of stock" text labels, not colour alone).
  • Search — 300 ms debounce, trimmed, server-side (q); the same substring match the web admin uses.
  • Filters & sort — bottom sheets for status/category/brand and an 8-option sort menu, all mapped to the API's own parameters; lookup lists load lazily the first time the filter sheet opens. Active filter chips carry their own labels, so they never depend on the lookup cache.
  • Pagination — infinite scroll uses gesture, end-of-data, in-flight, placeholder, and retry guards. The senior-review re-arm defect (drag-start and momentum-start both armed the same ref, letting one strong fling request two pages 441 ms apart) is fixed: the guard now arms exactly once per physical gesture, at drag start only, and momentum no longer re-arms it. Timestamped-proxy re-verification confirmed one request per gesture across plain, search, filtered, sorted, and combined datasets. The backend-reported total still decides when the list ends ("You've reached the end").
  • Result count comes from the backend's total for the filtered dataset — never the number of loaded rows.
  • Refresh — pull-to-refresh and the explicit Refresh action share one protected pipeline; the freshness indicator shows the age of the visible data.
  • States — skeleton rows on first load, previous results retained while a new dataset loads, dedicated empty/zero-result and error+retry states.
  • Keşfe dönük satırlar — görsel, ad, marka, fiyat ve stok durumunu taşıyan bir bilgi şeridi ("Düşük stok"/"Stokta yok" metin etiketleriyle, yalnızca renkle değil).
  • Arama — 300 ms debounce, boşlukları kırpılmış, sunucu tarafında (q); web admin'deki alt dize eşleşmesinin aynısı.
  • Filtreler ve sıralama — durum/kategori/marka için bottom sheet'ler ve 8 seçenekli bir sıralama menüsü; hepsi API'nin kendi parametrelerine eşlenir. Lookup listeleri, filtre sheet'i ilk açıldığında lazy yüklenir. Aktif filtre çipleri kendi etiketlerini taşır, bu yüzden lookup cache'ine bağımlı değiller.
  • Pagination — infinite scroll; jest, veri sonu, in-flight istek, placeholder ve retry korumalarıyla çalışır. Senior review'ın bulduğu yeniden kurulma hatası (drag başlangıcı ile momentum başlangıcının aynı ref'i kurması, tek güçlü bir fling'in 441 ms arayla iki sayfa istemesine yol açıyordu) düzeltildi: koruma artık fiziksel hareket başına tam bir kez, yalnızca drag başlangıcında kurulur ve momentum onu yeniden kurmaz. Zaman damgalı proxy ile yapılan yeniden doğrulama; düz, aramalı, filtreli, sıralı ve birleşik veri kümelerinde hareket başına tek istek davranışını teyit etti. Listenin nerede bittiğine yine backend'in bildirdiği toplam karar verir ("Sona ulaştınız").
  • Sonuç sayısı, filtrelenmiş veri kümesi için backend'in verdiği total değerinden gelir — asla yüklenmiş satır sayısından değil.
  • Yenileme — pull-to-refresh ile açık Yenile eylemi tek bir korumalı hattı paylaşır; tazelik göstergesi görünen verinin yaşını gösterir.
  • Durumlar — ilk yüklemede skeleton satırlar, yeni veri kümesi yüklenirken önceki sonuçların korunması, boş/sonuç yok ve hata+tekrar dene için ayrı durumlar.

Product detail & the stock workflow

Ürün detayı ve stok akışı

The detail screen leads with a hero card (image, name, price, status) and puts current stock immediately beside the editor — the one raised surface on the screen. The information section contains SKU, barcode, category, brand, unit, status, last-updated time, and the product description.

Detay ekranı bir hero kartıyla başlar (görsel, ad, fiyat, durum) ve mevcut stoğu doğrudan editörün yanına koyar — ekrandaki tek yükseltilmiş yüzey. Bilgi bölümünde SKU, barkod, kategori, marka, birim, durum, son güncelleme zamanı ve ürün açıklaması bulunur.

Only the current product detail is polled: approximately every 10 s, anchored to the last request settle, while this screen is focused and the app is active. Backgrounding or leaving the screen stops the timer; foreground/refocus triggers targeted detail revalidation. Incoming data follows the server when the stock draft is clean and shows a “changed elsewhere” notice without overwriting a dirty draft.

Yalnızca açık ürünün detayı poll edilir: bu ekran odaktayken ve uygulama aktifken, son fetch'in bitişine hizalanmış biçimde yaklaşık 10 saniyede bir. Arka plana geçmek veya ekrandan ayrılmak zamanlayıcıyı durdurur; ön plana/odağa dönüş yalnızca bu detayı yeniden doğrular. Stok taslağı temizse gelen veri sunucuyu izler; taslak kirliyse üzerine yazılmaz, bunun yerine “başka yerde değişti” uyarısı gösterilir.

Discontinued products are stock-locked. The editor disables its controls and shows a localized notice — but the real protection is server-side: the backend rejects the update with 409. A device that opened the product while it was Active and saves after head office discontinued it gets a definitive rejection, a specific message, and a detail refetch that flips the screen into the locked presentation. See the backend report.
Discontinued ürünlerde stok kilitlidir. Editör kontrollerini devre dışı bırakır ve yerelleştirilmiş bir uyarı gösterir — ama asıl koruma sunucu tarafında: backend güncellemeyi 409 ile reddeder. Ürünü Active durumdayken açan ve genel merkez ürünü Discontinued yaptıktan sonra kaydeden bir cihaz kesin bir ret, duruma özel bir mesaj ve ekranı kilitli görünüme geçiren bir detay refetch'i alır. Bkz. backend raporu.

Networking

Ağ yapılandırması

  • One variable: EXPO_PUBLIC_API_URL. Unset, it resolves to http://10.0.2.2:5080 on Android (the emulator's alias for the host machine — Android localhost is the device itself) and http://localhost:5080 elsewhere.
  • Physical devices and APKs set it explicitly to the host's LAN address; a hosted deployment would set an HTTPS URL through the same variable with no code change. There is deliberately no in-app server-settings screen.
  • Release builds bake the value in at JS-bundling time, which is why the delivered APK targets the emulator host and retargeting means a rebuild (documented in the README).
  • Cleartext HTTP is enabled via expo-build-properties only because the provided backend is HTTP-only; without it every network call in a release build fails.
  • Development uses a native debug build with Metro; expo-dev-client is a dev-build dependency and was verified inert in the release artifact (no dev-launcher activity, zero dev-menu entries). Debugging tooling is not part of the app's architecture.
  • Tek bir değişken: EXPO_PUBLIC_API_URL. Tanımlı değilse Android'de http://10.0.2.2:5080 (emülatörün host makine için kullandığı adres — Android'de localhost cihazın kendisidir), diğer ortamlarda http://localhost:5080 olur.
  • Fiziksel cihazlar ve APK'lar bunu host'un LAN adresine açıkça ayarlar; hosted bir deployment'ta da aynı değişkenle, kod değişikliği olmadan bir HTTPS URL'i verilirdi. Uygulama içinde bilinçli olarak bir sunucu ayarları ekranı yok.
  • Release build'ler değeri JS bundle'lama sırasında gömer; teslim edilen APK'nın emülatör host'unu hedeflemesinin ve hedef değiştirmenin yeniden build gerektirmesinin sebebi bu (README'de belgelendi).
  • Cleartext HTTP, yalnızca verilen backend HTTP-only olduğu için expo-build-properties üzerinden açıldı; o olmadan release build'deki her ağ çağrısı başarısız olur.
  • Geliştirmede Metro ile çalışan native bir debug build kullanılır; expo-dev-client bir dev build bağımlılığıdır ve release çıktısında etkisiz kaldığı doğrulandı (dev-launcher activity'si yok, dev-menu girdisi sıfır). Debug araçları uygulama mimarisinin parçası değil.

Localization

Yerelleştirme

English (default) and Turkish, switchable at runtime and persisted, via a small typed message catalog — the same approach as web. Chrome, states, validation, and status labels are localized; API data (product, brand, category names) never is. Backend error prose is never string-matched: failures are identified by status code plus request context and mapped to localized messages, with a generic localized fallback otherwise. Prices are always TRY, formatted from integer kuruş with locale-aware separators (₺39,50 tr / ₺39.50 en) and an explicit ₺ prefix, because Hermes renders the currency code instead of the symbol.

İngilizce (varsayılan) ve Türkçe; çalışma anında değiştirilebilir ve kalıcıdır, küçük ve tipli bir mesaj kataloğuyla — web'dekiyle aynı yaklaşım. Arayüz metinleri, durumlar, validasyon ve durum etiketleri yerelleştirilir; API verisi (ürün, marka, kategori adları) asla yerelleştirilmez. Backend'in hata metni hiçbir zaman string olarak eşleştirilmez: hatalar status kodu ve istek bağlamıyla tanınıp yerelleştirilmiş mesajlara eşlenir; kalanlar genel, yerelleştirilmiş bir mesaja düşer. Fiyatlar her zaman TRY'dir; tam sayı kuruş değerinden, locale'e duyarlı ayırıcılarla (₺39,50 tr / ₺39.50 en) ve açık bir ₺ önekiyle formatlanır — Hermes, sembol yerine para birimi kodunu bastığı için.

Why Expo (managed)

Neden Expo (managed)

The assignment leaves Expo vs bare React Native open. Managed Expo keeps native configuration declarative — the cleartext-HTTP flag, icons, and build properties are config, not patched Gradle files — while expo prebuild produces a full native project on demand, so the APK is built locally with plain Gradle and no cloud account or build queue. Rationale, alternatives, and the signing caveat: engineering decisions.

Assignment, Expo ile bare React Native arasındaki seçimi açık bırakıyor. Managed Expo, native yapılandırmayı declarative tutar — cleartext HTTP bayrağı, ikonlar ve build ayarları yamalanmış Gradle dosyaları değil, birer config'dir — expo prebuild ise istendiğinde tam bir native proje üretir; böylece APK, cloud hesabı veya build kuyruğu olmadan düz Gradle ile lokalde derlenir. Gerekçe, alternatifler ve imzalama uyarısı: mühendislik kararları.

Mobile UI philosophy

Mobil UI yaklaşımı

Surface hierarchy instead of outlines: a stone ground, borderless white content cards with faint elevation, filled (not bordered) controls, and exactly one raised surface per screen — the stock editor, because that is the screen's job. One brand-ish blue reserved for primary actions; semantic colours (danger/warning/success) carry the same meanings as the web admin's and are never repurposed for emphasis. Every stock numeral uses tabular figures. Snackbars are queued and bottom-anchored; sheets keep their actions above the gesture nav bar. The full token set and conventions are recorded in mobile/DESIGN.md.

Çerçeve yerine yüzey hiyerarşisi: taş renginde bir zemin, hafif yükseltili çerçevesiz beyaz içerik kartları, çerçeveli değil dolgulu kontroller ve ekran başına tam olarak bir yükseltilmiş yüzey — stok editörü, çünkü ekranın işi o. Birincil eylemlere ayrılmış tek bir marka mavisi; semantik renkler (danger/warning/success) web admin'deki anlamların aynısını taşır ve asla vurgu amacıyla kullanılmaz. Her stok rakamı tabular rakamla dizilir. Snackbar'lar kuyruğa alınır ve alta sabitlenir; sheet'ler eylemlerini gesture nav bar'ının üstünde tutar. Token setinin tamamı ve kurallar mobile/DESIGN.md içinde kayıtlı.

Trade-offs and limitations

Trade-off'lar ve sınırlar

  • Hand-styled UI costs more styling effort than a component kit, accepted to keep the dependency set minimal — the hardest piece (queued snackbars) would have needed custom code anyway.
  • Fixed API target in the APK — by design (configuration over UI surface); retargeting is a documented rebuild.
  • Debug-keystore signing — assignment-grade, not a store-ready signature.
  • Last-write-wins for stock, except the Discontinued rule; the app surfaces "changed elsewhere" rather than pretending to prevent it.
  • Pagination HIGH — fixed — the guard now arms once per physical gesture (drag start only; momentum no longer re-arms), and proxy re-verification confirmed one page request per gesture; see the implementation report for the evidence trail.
  • Stock-sort cache order — accepted — a successful save patches values without refetching, so stock/updated-time sorted lists can remain out of order until refresh. Explicitly accepted by the coordinator: the value shown is correct, and a normal refresh restores canonical ordering.
  • Product images require internet (the seed data points at a public placeholder service); failures degrade gracefully so they don't read as app failures.
  • Android-verified only — the assignment asks for an Android APK; iOS is unbuilt though the code paths exist.
  • Elle tasarlanmış UI, hazır bir bileşen kitine göre daha fazla stil emeği demek; bağımlılıkları en azda tutmak için kabul edildi — en zor parça (kuyruğa alınan snackbar'lar) zaten özel kod gerektirecekti.
  • APK içinde sabit API hedefi — tasarım gereği (ayar ekranı yerine konfigürasyon); hedef değiştirmek, belgelenmiş bir yeniden build.
  • Debug keystore ile imzalama — assignment düzeyinde, mağazaya hazır bir imza değil.
  • Stokta last-write-wins, Discontinued kuralı hariç; uygulama bunu engelliyormuş gibi yapmak yerine "başka yerde değişti" uyarısını gösterir.
  • YÜKSEK öncelikli pagination hatası — düzeltildi — koruma artık fiziksel hareket başına bir kez kurulur (yalnızca drag başlangıcında; momentum yeniden kurmaz) ve proxy ile yeniden doğrulama, hareket başına tek sayfa isteğini teyit etti; kanıt zinciri için implementation raporuna bakın.
  • Stok sıralamasında cache sırası — kabul edildi — başarılı kayıt, değerleri refetch yapmadan yamaladığı için stok ya da güncelleme zamanına göre sıralı listeler yenilemeye kadar eski sırada kalabilir. Koordinatör tarafından bilinçli olarak kabul edildi: gösterilen değer doğrudur ve normal bir yenileme kanonik sıralamayı geri getirir.
  • Ürün görselleri internet gerektirir (seed verisi herkese açık bir placeholder servisini gösteriyor); görsel hataları sessizce tolere edilir, uygulama hatası gibi görünmez.
  • Yalnızca Android'de doğrulandı — assignment bir Android APK istiyor; kod yolları mevcut olsa da iOS derlenmedi.
