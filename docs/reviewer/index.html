One product, two operational surfaces

Tek ürün, iki operasyonel yüzey

A head-office web admin and a store-floor mobile app built over the provided StokMate .NET API, sharing a single framework-free TypeScript API/auth core. Delivered as source, a verified Android APK, and this documentation set. How to run everything: the repository README.

Verilen StokMate .NET API'si üzerine kurulan, genel müdürlük için bir web yönetim paneli ve mağaza sahası için bir mobil uygulama; ikisi de framework içermeyen tek bir TypeScript API/auth çekirdeğini paylaşır. Kaynak kod, doğrulanmış bir Android APK ve bu dokümantasyon seti olarak teslim edildi. Her şeyin nasıl çalıştırılacağı: depo README'si.

System overview

Sisteme genel bakış

What this delivery optimized for

Bu teslimde neye öncelik verildi

Assignment completeness

Every required feature plus all three optional bonuses, verified against written acceptance criteria — never features for their own sake.

Ödev bütünlüğü

Zorunlu özelliklerin tamamı ve üç opsiyonel bonusun hepsi, yazılı kabul ölçütlerine göre doğrulandı — özellik olsun diye özellik eklenmedi.

API correctness

The backend's real behavior was verified at runtime and recorded before client code depended on it; clients never invent API behavior.

API doğruluğu

Backend'in gerçek davranışı, istemci kodu ona bağımlı hâle gelmeden önce çalışır hâlde doğrulanıp kayda geçirildi; istemciler API davranışı uydurmaz.

Admin / customer separation

The web admin is dense and operational; the mobile app is a productized customer surface. Deliberately different designs over one shared data language.

Yönetici / müşteri ayrımı

Web yönetim paneli yoğun ve operasyonel; mobil uygulama ürünleşmiş bir müşteri yüzeyi. Tek bir ortak veri dili üzerinde bilinçli olarak farklı tasarımlar.

Predictable data flow

One server-state layer (TanStack Query), one API client, one refresh pipeline per dataset — every data movement has a single, inspectable path.

Öngörülebilir veri akışı

Tek bir server-state katmanı (TanStack Query), tek bir API client'ı, veri kümesi başına tek bir yenileme hattı — her veri hareketinin tek ve incelenebilir bir yolu var.

Data freshness

The brief left the mechanism open: coordinated polling/refetch exposes cross-client changes through one data path; no realtime transport was added, and the server independently limits reads.

Veri tazeliği

Ödev mekanizmayı açık bıraktı: koordineli polling/refetch, istemciler arası değişiklikleri tek veri yolunda gösterir; realtime taşıma eklenmedi ve sunucu okumaları bağımsız olarak sınırlar.

Explicit product assumptions

Where the brief was silent: Discontinued is terminal for stock (Passive is not), mobile defaults to Active while web defaults to All, low-stock cues use only minStock, and the lossless detail read plus read limit are deliberately narrow additions.

Açık ürün varsayımları

Ödevin sustuğu noktalarda: stok için Discontinued terminaldir (Pasif değil), mobil Aktif web Tümü ile açılır, düşük stok yalnızca minStock ile gösterilir; kayıpsız detay okuması ve okuma limiti bilinçli olarak dar eklerdir.

Engineering highlights

Öne çıkan mühendislik noktaları

  • Single-flight token refresh with a session-epoch guard — strict refresh-token rotation makes concurrent refreshes fatal; the shared client makes them structurally impossible, and stale in-flight requests can neither resurrect a logged-out session nor tear down a new one (shared/src/api/client.ts).
  • A proven data-loss trap, closed at the source — the provided PUT is a full replace requiring fields no read endpoint returned; discovery proved any legal client PUT silently corrupted data, and the minimal GET /products/{id} addition makes edits losslessly round-trippable.
  • Coordinated freshness pipeline — manual refresh, pull-to-refresh, focus revalidation, mutation invalidation, and background polls all converge on one query fetch; polls re-anchor to the last fetch settle so triggers never stack, with backend rate limiting as the independent boundary.
  • Server-enforced domain rule for stale clients — a stock update on a Discontinued product is rejected with 409 by the backend, so a device that opened the product while it was Active cannot book stock onto it after head office discontinues it.
  • Evidence-based QA — the delivered APK itself (not a dev build) passed a 12-point standalone matrix with independent curl read-backs; "done" claims required executed evidence throughout.
  • Session-epoch korumalı single-flight token yenileme — katı refresh token rotasyonu eşzamanlı yenilemeleri ölümcül kılıyor; paylaşılan client bunu yapısal olarak imkânsız hâle getiriyor ve uçuştaki bayat istekler ne kapanmış bir oturumu diriltebiliyor ne de yeni bir oturumu düşürebiliyor (shared/src/api/client.ts).
  • Kanıtlanmış bir veri kaybı tuzağı, kaynağında kapatıldı — verilen PUT, hiçbir okuma endpoint'inin döndürmediği alanları zorunlu kılan tam bir değiştirme işlemi; keşif aşaması, kurallara uygun her istemci PUT'unun veriyi sessizce bozduğunu kanıtladı ve minimal GET /products/{id} eklemesi düzenlemeleri kayıpsız gidip gelebilir hâle getirdi.
  • Koordineli tazelik hattı — manuel yenileme, pull-to-refresh, odaklanmada yeniden doğrulama, mutation invalidasyonu ve arka plan polling'i tek bir query fetch'inde birleşiyor; polling son fetch'in tamamlanmasına yeniden bağlandığı için tetikleyiciler üst üste binmiyor, backend rate limiting ise bağımsız sınır olarak duruyor.
  • Bayat istemciler için sunucuda zorlanan iş kuralı — Discontinued bir ürüne yapılan stok güncellemesi backend tarafından 409 ile reddediliyor; böylece ürünü Active durumdayken açmış bir cihaz, genel müdürlük ürünü durdurduktan sonra ona stok işleyemiyor.
  • Kanıta dayalı QA — teslim edilen APK'nın kendisi (dev build değil) bağımsız curl okumalarıyla 12 maddelik bağımsız matrisi geçti; süreç boyunca "tamamlandı" iddiaları yürütülmüş kanıt gerektirdi.

Suggested review path

Önerilen inceleme sırası

  1. Run the stack with the README quick start (backend → web → mobile) and click through both clients with the test user.
  2. Skim this overview's system diagram, then read the web admin report and mobile report — state ownership and data flow are the load-bearing sections.
  3. Read the backend report for exactly what was provided vs. modified, and why each modification exists.
  4. Read the engineering decisions for rationale, alternatives, and rejected complexity.
  5. Finish with the AI-assisted workflow report — how the project was actually built, verified, and kept in scope.
  1. Yığını README hızlı başlangıcıyla çalıştırın (backend → web → mobil) ve test kullanıcısıyla her iki istemcide de gezinin.
  2. Buradaki sistem diyagramına göz atın, ardından web yönetim paneli raporunu ve mobil raporu okuyun — state sahipliği ve veri akışı taşıyıcı bölümler.
  3. Nelerin verildiğini, nelerin değiştirildiğini ve her değişikliğin neden var olduğunu görmek için backend raporunu okuyun.
  4. Gerekçeler, alternatifler ve reddedilen karmaşıklık için mühendislik kararlarını okuyun.
  5. Yapay zekâ destekli süreç raporuyla bitirin — proje gerçekte nasıl inşa edildi, doğrulandı ve kapsamda tutuldu.
