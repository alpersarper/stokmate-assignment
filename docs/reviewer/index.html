One product, two operational surfaces

Tek ürün, iki operasyonel yüzey

A head-office web admin and a store-floor mobile app built over the provided StokMate .NET API, sharing a single framework-free TypeScript API/auth core. Delivered as source, a verified Android APK, and this documentation set. How to run everything: the repository README.

Verilen StokMate .NET API'si üzerinde, genel merkez için bir web admin paneli ve mağaza sahası için bir mobil uygulama; ikisi de framework bağımsız tek bir TypeScript API/auth çekirdeğini paylaşır. Teslimat: kaynak kod, doğrulanmış bir Android APK ve bu dokümantasyon seti. Çalıştırma adımları için repo README'sine bakın.

System overview

Sisteme genel bakış

What this delivery optimized for

Bu teslimde neye öncelik verildi

Assignment completeness

The required vertical slices and optional refresh work are implemented; current verification evidence, including the open pagination defect, is reported without converting historical passes into guarantees.

Assignment bütünlüğü

Zorunlu dikey akışlar ve opsiyonel yenileme özelliği uygulandı; güncel doğrulama kanıtı — açık pagination hatası dâhil — geçmişte geçen testler garanti sayılmadan raporlanıyor.

API correctness

The backend's real behavior was verified at runtime and recorded before client code depended on it; clients never invent API behavior.

API doğruluğu

Backend'in gerçek davranışı, istemci kodu ona bağımlı hâle gelmeden önce runtime'da doğrulanıp kayda geçirildi; istemciler hiçbir API davranışını varsaymaz.

Admin / customer separation

The web admin is dense and operational; the mobile app is a productized customer surface. Deliberately different designs over one shared data language.

Admin / müşteri ayrımı

Web admin paneli yoğun ve operasyonel; mobil uygulama ürünleşmiş bir müşteri yüzeyi. Ortak tek veri dili üzerinde, bilinçli olarak farklı iki tasarım.

Predictable data flow

One server-state layer (TanStack Query), one API client, one refresh pipeline per dataset — every data movement has a single, inspectable path.

Öngörülebilir veri akışı

Tek server-state katmanı (TanStack Query), tek API client'ı, veri kümesi başına tek yenileme hattı — her veri hareketinin izlenebilir tek bir yolu var.

Data freshness

The brief left the mechanism open: coordinated polling/refetch exposes cross-client changes through one data path; no realtime transport was added, and the server independently limits reads.

Veri tazeliği

Assignment mekanizma seçimini açık bırakmıştı: koordineli polling/refetch, istemciler arası değişiklikleri tek veri yolu üzerinden görünür kılar; realtime bir kanal eklenmedi, read'leri de sunucu bağımsız olarak sınırlar.

Explicit product assumptions

Where the brief was silent: Discontinued is terminal for stock (Passive is not), mobile defaults to Active while web defaults to All, low-stock cues use only minStock, and the lossless detail read plus read limit are deliberately narrow additions.

Açık ürün varsayımları

Assignment'ın sustuğu noktalarda: stok için Discontinued terminaldir (Passive değildir), mobil varsayılan olarak Active, web ise All ile açılır, düşük stok vurgusu yalnızca minStock'a dayanır; kayıpsız detay okuması ve read rate limit'i bilinçli olarak dar tutulmuş eklemelerdir.

Engineering highlights

Öne çıkan mühendislik noktaları

  • Single-flight token refresh with a session-epoch guard — strict refresh-token rotation makes concurrent refreshes fatal; the shared client makes them structurally impossible, and stale in-flight requests can neither resurrect a logged-out session nor tear down a new one (shared/src/api/client.ts).
  • A proven data-loss trap, closed at the source — the provided PUT is a full replace requiring fields no read endpoint returned; discovery proved any legal client PUT silently corrupted data, and the minimal GET /products/{id} addition makes edits losslessly round-trippable.
  • Coordinated freshness pipeline — the visible web list polls its current query about every 15 s; the focused, foreground mobile detail polls only its current product about every 10 s. Manual/lifecycle reads join the same per-key pipeline; mobile stock success patches caches without a follow-up GET. Polls re-anchor to the last fetch settle, with backend rate limiting as the independent boundary.
  • Server-enforced domain rule for stale clients — a stock update on a Discontinued product is rejected with 409 by the backend, so a device that opened the product while it was Active cannot book stock onto it after head office discontinues it.
  • Evidence-based QA — the delivered APK itself (not a dev build) passed a 12-point standalone matrix with independent curl read-backs; "done" claims required executed evidence throughout.
  • Session-epoch korumalı single-flight token refresh'i — katı refresh token rotasyonunda eşzamanlı refresh istekleri oturumu düşürür; paylaşılan client bunu yapısal olarak imkânsız kılar. Yanıtı hâlâ yolda olan stale bir istek ne kapanmış bir oturumu geri getirebilir ne de yeni açılan bir oturumu bozabilir (shared/src/api/client.ts).
  • Kanıtlanmış bir veri kaybı tuzağı, kaynağında kapatıldı — verilen PUT, hiçbir read endpoint'inin döndürmediği alanları zorunlu tutan bir full-replace. Keşif aşamasında, kurallara uygun her istemci PUT'unun veriyi sessizce bozduğu kanıtlandı; minimal GET /products/{id} eklemesi düzenlemeleri kayıpsız hâle getirdi.
  • Koordineli tazelik hattı — ekranda görünen web listesi, açık query'sini yaklaşık 15 saniyede bir; ön plandaki mobil detay ekranı yalnızca açık ürünü yaklaşık 10 saniyede bir poll eder. Manuel ve yaşam döngüsü kaynaklı read'ler aynı key bazlı hatta katılır; başarılı bir mobil stok kaydı, ek bir GET atmadan cache'leri günceller. Polling her fetch'in bitişine göre yeniden hizalanır; backend'deki rate limit ise bundan bağımsız bir sınırdır.
  • Stale istemcilere karşı sunucuda uygulanan domain kuralı — Discontinued bir ürüne stok güncellemesi backend tarafından 409 ile reddedilir; ürünü Active'ken açmış bir cihaz, genel merkez ürünü Discontinued yaptıktan sonra ona stok yazamaz.
  • Kanıta dayalı QA — teslim edilen APK'nın kendisi (dev build değil), bağımsız curl geri okumaları içeren 12 maddelik standalone matrisi geçti; süreç boyunca hiçbir "tamamlandı" iddiası, çalıştırılmış kanıt olmadan kabul edilmedi.

Suggested review path

Önerilen inceleme sırası

  1. Run the stack with the README quick start (backend → web → mobile) and click through both clients with the test user.
  2. Skim this overview's system diagram, then read the web admin report and mobile report — state ownership and data flow are the load-bearing sections.
  3. Read the backend report for exactly what was provided vs. modified, and why each modification exists.
  4. Read the engineering decisions for rationale, alternatives, and rejected complexity.
  5. Finish with the AI-assisted workflow report — how the project was actually built, verified, and kept in scope.
  1. Stack'i README'deki hızlı başlangıçla ayağa kaldırın (backend → web → mobil) ve test kullanıcısıyla iki istemcide de gezinin.
  2. Bu sayfadaki sistem diyagramına göz attıktan sonra web admin raporunu ve mobil raporu okuyun — asıl yük, state sahipliği ve veri akışı bölümlerinde.
  3. Neyin verildiğini, neyin değiştirildiğini ve her değişikliğin gerekçesini görmek için backend raporunu okuyun.
  4. Gerekçeler, alternatifler ve bilerek eklenmeyen karmaşıklık için mühendislik kararlarına geçin.
  5. Yapay zekâ destekli süreç raporuyla bitirin — proje gerçekte nasıl geliştirildi, doğrulandı ve kapsam içinde tutuldu.
