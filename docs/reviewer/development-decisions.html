1 · One repository, npm workspaces

1 · Tek depo, npm workspaces

Context
Two clients that must agree exactly on types and API behavior, plus the provided backend, delivered as one submission.
Decision
A flat npm-workspaces monorepo: shared, web, mobile, with the backend alongside. shared ships TypeScript source directly — no build step, no project references.
Why
One install, one dependency tree, one lockfile. npm ships with Node, so a reviewer needs no extra tooling, and it has the fewest React Native/Metro edge cases. Vite transpiles workspace TypeScript and Metro compiles through Babel, so source-only sharing just works.
Alternatives
pnpm — faster, but adds an install step for the reviewer and occasional Metro friction whose standard mitigation reproduces npm's layout anyway. Separate folders without workspaces — duplicated types and client code. Nx/Turborepo — a build graph for three packages.
Trade-off
npm's flat node_modules is less strict about phantom dependencies than pnpm's isolated layout.
Result
A reviewer runs npm install once at the root and everything works, including the mobile build.
Bağlam
Tipler ve API davranışı konusunda birebir anlaşması gereken iki istemci ve verilen backend, tek bir teslimat olarak sunuluyor.
Karar
Düz bir npm-workspaces monorepo'su: shared, web, mobile; backend de yanlarında. shared doğrudan TypeScript kaynağı yayımlıyor — build adımı yok, project reference yok.
Gerekçe
Tek install, tek bağımlılık ağacı, tek lockfile. npm Node ile birlikte geldiği için değerlendirici ek araç kurmuyor; ayrıca React Native/Metro uç durumları en az olan seçenek. Vite workspace TypeScript'ini transpile ediyor, Metro Babel üzerinden derliyor; bu yüzden yalnızca kaynak paylaşmak sorunsuz çalışıyor.
Değerlendirilen alternatifler
pnpm — daha hızlı, ama değerlendirici için ek bir kurulum adımı ve zaman zaman Metro sürtüşmesi getiriyor; standart çözümü de zaten npm'in yerleşimini yeniden üretiyor. Workspace'siz ayrı klasörler — tiplerin ve istemci kodunun tekrarlanması. Nx/Turborepo — üç paket için build grafiği.
Trade-off
npm'in düz node_modules yapısı, phantom bağımlılıklar konusunda pnpm'in izole yerleşiminden daha gevşek.
Sonuç
Değerlendirici kökte bir kez npm install çalıştırıyor ve mobil build dahil her şey çalışıyor.

2 · Share the wire, not the UI

2 · Wire katmanını paylaş, UI'ı değil

Context
Two clients, one API with several verified traps (full-replace PUT, plain-text errors, strict token rotation).
Decision
Share only framework-free code whose behavior is genuinely identical on both platforms: API/domain types, the fetch client core, the query-key factory, and small formatting/normalization utilities. UI, navigation, forms, and storage stay per-app; each app injects its own storage adapter.
Why
The plumbing that must be exactly right — error normalization, Bearer injection, refresh-and-retry — is implemented once and gets one set of tests. Query keys are shared so cache and invalidation semantics can't drift between clients.
Alternatives
A shared UI component package — rejected: DOM and React Native primitives don't share cleanly at this scale and the result is lowest-common-denominator components. Duplicating the client per app — two places to get token rotation wrong.
Trade-off
A little indirection: platform behavior enters through injected adapters rather than being inline.
Result
Roughly 500 lines of shared source carry every cross-client correctness concern, covered by unit tests plus live contract tests against the running backend.
Bağlam
İki istemci ve doğrulanmış birkaç tuzağı olan tek bir API (full-replace PUT, düz metin hatalar, katı token rotasyonu).
Karar
Yalnızca framework bağımsız ve davranışı iki platformda gerçekten aynı olan kod paylaşılıyor: API/domain tipleri, fetch client'ının çekirdeği, query key factory'si ve küçük formatlama/normalizasyon yardımcıları. UI, navigasyon, formlar ve depolama uygulamaya özel kalıyor; her uygulama kendi storage adapter'ını enjekte ediyor.
Gerekçe
Birebir doğru olması gereken altyapı — hata normalizasyonu, Bearer ekleme, refresh-and-retry — bir kez yazılıyor ve tek bir test kümesiyle korunuyor. Query key'ler paylaşıldığı için cache ve invalidation semantiği istemciler arasında ayrışamıyor.
Değerlendirilen alternatifler
Paylaşılan bir UI bileşen paketi — reddedildi: DOM ve React Native primitive'leri bu ölçekte temiz paylaşılamıyor ve sonuç, en düşük ortak paydada bileşenler oluyor. İstemciyi her uygulamada ayrı yazmak — token rotasyonunu yanlış yapmak için iki ayrı yer.
Trade-off
Bir miktar dolaylılık: platform davranışı satır içinde değil, enjekte edilen adapter'lar üzerinden giriyor.
Sonuç
Yaklaşık 500 satır paylaşılan kaynak, istemciler arası tüm doğruluk kaygılarını taşıyor; unit testlerin yanı sıra çalışan backend'e karşı canlı kontrat testleriyle kapsanıyor.

3 · TanStack Query as the only server-state layer

3 · Tek server-state katmanı olarak TanStack Query

Context
Almost all application state in this product is server state. (Using TanStack Query was a fixed project decision; it was adopted willingly.)
Decision
TanStack Query v5 on both clients, with no additional state library. Remaining client state is one auth context plus local component state.
Why
Query keys per filter combination give stale-response protection for free — a late response lands under its own key and can never overwrite the current view. keepPreviousData delivers the required "keep results visible while loading" behavior natively, and invalidation delivers "the list shows persisted state after an update".
Alternatives
Redux/Zustand/Jotai on top — would duplicate a cache that already exists. Hand-rolled fetching hooks — reimplements deduplication, caching, and revalidation badly.
Trade-off
No optimistic updates by design: the UX contract requires showing persisted server state after a save, so optimism would add rollback complexity for no required behavior.
Result
No global store exists in either client, and none is missing.
Bağlam
Bu üründeki uygulama state'inin neredeyse tamamı server state. (TanStack Query kullanımı sabit bir proje kararıydı; isteyerek benimsendi.)
Karar
Her iki istemcide de TanStack Query v5, ek bir state kütüphanesi olmadan. Geriye kalan istemci state'i tek bir auth context ve yerel bileşen state'i.
Gerekçe
Her filtre kombinasyonuna ayrı query key vermek, stale yanıtlara karşı korumayı beraberinde getiriyor — geç gelen bir yanıt kendi key'ine düşüyor ve mevcut görünümün üzerine asla yazamıyor. keepPreviousData gereken "yüklenirken sonuçları görünür tut" davranışını doğrudan veriyor, invalidation da "liste, güncellemeden sonra sunucudaki kalıcı state'i gösterir" gereksinimini karşılıyor.
Değerlendirilen alternatifler
Üzerine Redux/Zustand/Jotai — zaten var olan bir cache'i tekrarlardı. Elle yazılmış fetch hook'ları — deduplication, cache ve revalidation'ı kötü biçimde yeniden yazmak demek.
Trade-off
Tasarım gereği optimistic update yok: UX kararı, kayıttan sonra sunucuda kalıcı hâle gelen state'in gösterilmesini istiyor; dolayısıyla optimistic update, gerekli olmayan bir davranış için rollback karmaşıklığı eklerdi.
Sonuç
İki istemcide de global store yok ve eksikliği de hissedilmiyor.

4 · Centralized, single-flight 401 → refresh → retry

4 · Merkezî, single-flight 401 → refresh → yeniden deneme

Context
Verified backend behavior: 15-minute access tokens; refresh tokens rotate strictly (replaying one kills the session); logout on one client invalidates the other's access tokens immediately; a backend restart wipes every session.
Decision
One interceptor in the shared client: on 401, refresh once behind a mutex, persist the new pair before resolving, retry the original request exactly once. Refresh failure clears storage and returns the app to login. A session-epoch counter invalidates in-flight handling across login/logout boundaries.
Why
This is required plumbing, not an enhancement — without it both apps appear randomly broken mid-use. Rotation makes concurrent refreshes fatal, so single-flight is a correctness requirement, not an optimization.
Alternatives
Proactive expiry timers — clock-skew and lifecycle complexity for no benefit over reactive refresh. Per-app implementations — two chances to get rotation wrong. Shared token storage between clients — each client legitimately owns its own session chain.
Trade-off
The first request after expiry pays one extra round trip.
Result
Session-expiry, cross-client-logout, and backend-restart recovery were all exercised end-to-end, including in the release APK.
Bağlam
Doğrulanmış backend davranışı: 15 dakikalık access token'lar; refresh token'lar katı biçimde rotasyona giriyor (birini tekrar kullanmak oturumu öldürüyor); bir istemcideki logout, diğerinin access token'larını anında geçersiz kılıyor; backend yeniden başlatıldığında tüm oturumlar siliniyor.
Karar
Paylaşılan client'ta tek bir interceptor: 401'de bir mutex arkasında bir kez refresh, yeni çift promise çözülmeden önce kalıcılaştırılıyor, orijinal istek tam olarak bir kez tekrarlanıyor. Refresh başarısız olursa storage temizleniyor ve uygulama login'e dönüyor. Oturum-epoch sayacı, login/logout sınırlarında devam eden isteklerin sonuçlarını geçersiz kılıyor.
Gerekçe
Bu bir iyileştirme değil, zorunlu altyapı — olmadan iki uygulama da kullanım sırasında rastgele bozulmuş görünüyor. Rotasyon yüzünden eşzamanlı refresh'ler oturumu düşürdüğü için single-flight bir optimizasyon değil, doğruluk gereksinimi.
Değerlendirilen alternatifler
Süre dolmadan önden çalışan expiry timer'ları — reaktif refresh'e göre hiçbir kazanç sağlamadan saat kayması ve yaşam döngüsü karmaşıklığı. Uygulama başına ayrı implementasyonlar — rotasyonu yanlış yapmak için iki fırsat. İstemciler arasında ortak token depolama — her istemci kendi oturum zincirine haklı olarak sahip.
Trade-off
Süre dolduktan sonraki ilk istek fazladan bir gidiş-dönüş ödüyor.
Sonuç
Oturum süresinin dolması, istemciler arası logout ve backend yeniden başlatıldıktan sonra toparlanma uçtan uca denendi; release APK dahil.

5 · The web list state lives in the URL

5 · Web liste state'i URL'de yaşıyor

Context
The admin list carries search, three filters, sort, direction, and page — and the UX requires that returning from a product detail preserves all of it.
Decision
All of it lives in URL search params; the parsed params are the TanStack query key.
Why
"Preserve the view" comes for free from the browser's own history, and it survives reload, is shareable, and makes the displayed data and the address bar structurally incapable of disagreeing.
Alternatives
Component state plus a restoration mechanism — more code and a new class of bug (state and URL drifting apart).
Trade-off
Search input needs a 300 ms debounce before it reaches the URL, so typing doesn't spam history.
Result
Filter/sort/page state is inspectable in the address bar during review — e.g. ?status=3&sort=price&dir=desc.
Bağlam
Admin listesi arama, üç filtre, sıralama, yön ve sayfa taşıyor — UX ise ürün detayından dönüldüğünde bunların tamamının korunmasını gerektiriyor.
Karar
Hepsi URL search param'larında duruyor; parse edilen param'lar doğrudan TanStack query key'i oluyor.
Gerekçe
"Görünümü koru" davranışı tarayıcının kendi history'sinden kendiliğinden geliyor; ayrıca sayfa yenilemede kaybolmuyor, paylaşılabiliyor ve gösterilen veriyle adres çubuğunun çelişmesini yapısal olarak imkânsız kılıyor.
Değerlendirilen alternatifler
Bileşen state'i artı bir geri yükleme mekanizması — daha fazla kod ve yeni bir hata sınıfı (state ile URL'in birbirinden ayrışması).
Trade-off
Arama girdisinin URL'e ulaşmadan önce 300 ms debounce'a ihtiyacı var; böylece yazmak geçmişi doldurmuyor.
Sonuç
Filtre/sıralama/sayfa state'i inceleme sırasında adres çubuğundan görülebiliyor — ör. ?status=3&sort=price&dir=desc.

6 · shadcn/ui on Tailwind for the web admin

6 · Web admin için Tailwind üzerinde shadcn/ui

Context
An operational admin UI needing accessible primitives — table, select, dialog, toast — without adopting a design system.
Decision
shadcn/ui components vendored into the repository on Tailwind CSS v4; only the ~10 components the assignment needs.
Why
The components are owned source in the repo: inspectable, adaptable, and reviewable, with accessible Radix primitives underneath and a small dependency surface.
Alternatives
Mantine — a strong fit for the table/snackbar requirements (and the initial discovery recommendation), but a larger opaque dependency with its own styling system. MUI — heavier still. Hand-rolled CSS — the weakest accessibility for the effort.
Trade-off
Vendored components are code to maintain; the mitigation is composing rather than modifying primitives, with domain display logic kept in one place.
Result
A consistent admin surface that never grew into a design-system project.
Bağlam
Bir tasarım sistemi benimsemeden erişilebilir primitive'lere — tablo, select, dialog, toast — ihtiyaç duyan operasyonel bir admin UI'ı.
Karar
Tailwind CSS v4 üzerinde, repoya kopyalanmış shadcn/ui bileşenleri; yalnızca ödevin ihtiyaç duyduğu ~10 bileşen.
Gerekçe
Bileşenler repoda sahiplenilen kaynak kod: incelenebilir, uyarlanabilir ve gözden geçirilebilir; altta erişilebilir Radix primitive'leri ve küçük bir bağımlılık yüzeyi var.
Değerlendirilen alternatifler
Mantine — tablo/snackbar gereksinimlerine güçlü biçimde uyuyordu (ve ilk keşif önerisiydi), ama kendi stil sistemi olan, daha büyük ve kapalı bir bağımlılık. MUI — daha da ağır. Elle yazılmış CSS — harcanan emeğe karşılık en zayıf erişilebilirlik.
Trade-off
Repoya kopyalanan bileşenler, bakımı yapılacak koddur; azaltıcı önlem, primitive'leri değiştirmek yerine kompoze etmek ve domain gösterim mantığını tek yerde tutmak.
Sonuç
Hiçbir zaman bir tasarım sistemi projesine dönüşmeyen, tutarlı bir admin yüzeyi.

7 · Hand-styled mobile UI, no component kit

7 · Elle tasarlanmış mobil UI, bileşen kiti yok

Context
Four mobile screens plus feedback states, with queued bottom snackbars required by the UX decisions.
Decision
React Native StyleSheet with a small owned primitive set and a token file; no RN Paper or equivalent.
Why
The genuinely hard piece — a queued snackbar system — needs custom code even with a kit (Paper's is single-instance), so a kit would have added a dependency without removing work. It also keeps the mobile look free of a third-party visual identity.
Alternatives
React Native Paper — kept as an explicit escape hatch if velocity had suffered; it wasn't needed.
Trade-off
More styling effort, accepted for a minimal dependency set.
Result
A coherent surface system (documented in mobile/DESIGN.md) with two UI-related runtime dependencies: navigation and safe-area handling.
Bağlam
Dört mobil ekran ve geri bildirim durumları; UX kararlarının gerektirdiği, kuyruğa alınan alt snackbar'larla birlikte.
Karar
React Native StyleSheet, küçük ve sahiplenilen bir primitive kümesi ve bir token dosyası; RN Paper veya muadili yok.
Gerekçe
Asıl zor parça — kuyruğa alınan snackbar sistemi — bir kitle bile özel kod gerektiriyor (Paper'ınki tek instance'lı); yani bir kit, iş azaltmadan bağımlılık eklerdi. Ayrıca mobil görünümü üçüncü parti bir görsel kimlikten uzak tutuyor.
Değerlendirilen alternatifler
React Native Paper — hız düşerse diye açık bir çıkış kapısı olarak tutuldu; ihtiyaç olmadı.
Trade-off
Daha fazla stil emeği; minimal bir bağımlılık kümesi için kabul edildi.
Sonuç
UI ile ilgili yalnızca iki runtime bağımlılığı olan tutarlı bir yüzey sistemi (mobile/DESIGN.md içinde belgelendi): navigasyon ve safe-area yönetimi.

8 · Deliberately different designs for admin and mobile

8 · Admin ve mobil için bilinçli olarak farklı tasarımlar

Context
One product family, two audiences: head-office operators at a desk and store staff on a phone.
Decision
Share the data language — status semantics, stock thresholds, currency formatting, terminology — but not the visual system. Web is a dense operational table; mobile is a productized browsing-and-editing surface.
Why
Operators scan many rows and compare values; store staff hold a phone one-handed and act on one product. Forcing one visual system on both would compromise the primary task of each.
Alternatives
A shared component/design package — rejected for the same reason as shared UI code generally.
Trade-off
Two style systems to keep coherent; mitigated by recording both in DESIGN.md files so later passes extend rather than reinvent them.
Result
Each surface reads as fit for its user, while status colours and ₺ amounts mean the same thing everywhere.
Bağlam
Tek ürün ailesi, iki kitle: masa başındaki genel merkez operatörleri ve telefondaki mağaza personeli.
Karar
Veri dili paylaşılıyor — durum semantiği, stok eşikleri, para formatı, terminoloji — ama görsel sistem paylaşılmıyor. Web yoğun bir operasyonel tablo; mobil ise ürünleşmiş bir gezinme ve düzenleme yüzeyi.
Gerekçe
Operatörler çok sayıda satırı tarayıp değerleri karşılaştırıyor; mağaza personeli telefonu tek elle tutup tek bir ürün üzerinde işlem yapıyor. İkisine tek bir görsel sistem dayatmak, her birinin asıl işini zayıflatırdı.
Değerlendirilen alternatifler
Paylaşılan bir bileşen/tasarım paketi — genel olarak paylaşılan UI kodunun reddedilme gerekçesiyle aynı nedenle reddedildi.
Trade-off
Tutarlı tutulması gereken iki stil sistemi; her ikisinin de DESIGN.md dosyalarına kaydedilmesiyle hafifletiliyor, böylece sonraki geçişler onları yeniden icat etmek yerine genişletiyor.
Sonuç
Her yüzey kendi kullanıcısına uygun okunuyor; durum renkleri ve ₺ tutarları ise her yerde aynı anlama geliyor.

9 · Expo managed workflow, APK built locally with Gradle

9 · Expo managed workflow, APK lokalde Gradle ile build ediliyor

Context
The assignment requires a working Android APK; Expo vs bare React Native was left open.
Decision
Expo managed workflow; the deliverable APK produced by expo prebuild + local gradlew assembleRelease, signed with the Gradle debug keystore and documented as assignment-grade.
Why
No cloud build account or queue; reproducible offline; the reviewer can run the exact same documented commands. Managed Expo keeps native configuration declarative — including the cleartext-HTTP flag the HTTP-only backend requires — while prebuild yields the full native project when Gradle needs it.
Alternatives
EAS cloud build — an account and upload dependency for the reviewer's reproduction path. Bare React Native — permanent native-config maintenance in exchange for one-time prebuild output.
Trade-off
Debug-keystore signing is not store-ready, and the first Gradle build is slow and network-heavy.
Result
The delivered APK was built from a known commit and verified standalone on an emulator against the live backend — an APK that merely builds was explicitly not treated as done.
Bağlam
Ödev çalışan bir Android APK istiyor; Expo ile bare React Native arasındaki seçim açık bırakılmıştı.
Karar
Expo managed workflow; teslim edilecek APK expo prebuild + lokal gradlew assembleRelease ile üretiliyor, Gradle debug keystore'uyla imzalanıyor ve assignment düzeyinde olduğu belgeleniyor.
Gerekçe
Cloud build hesabı veya kuyruğu yok; offline yeniden üretilebilir; değerlendirici, belgelenen komutların tam olarak aynısını çalıştırabiliyor. Managed Expo native yapılandırmayı declarative tutuyor — yalnızca HTTP konuşan backend'in gerektirdiği cleartext HTTP bayrağı dâhil — prebuild ise Gradle'ın ihtiyaç duyduğu anda tam native projeyi üretiyor.
Değerlendirilen alternatifler
EAS cloud build'i — değerlendiricinin yeniden üretim yolu için hesap ve upload bağımlılığı. Bare React Native — tek seferlik prebuild çıktısı yerine kalıcı native config bakımı.
Trade-off
Debug keystore ile imzalama mağazaya hazır değil; ilk Gradle build'i de yavaş ve ağ yoğun.
Sonuç
Teslim edilen APK bilinen bir commit'ten build edildi ve emülatör üzerinde, çalışan backend'e karşı tek başına doğrulandı — yalnızca derlenebilen bir APK açıkça "tamamlandı" sayılmadı.

10 · One environment variable instead of a server-settings screen

10 · Sunucu ayarı ekranı yerine tek bir ortam değişkeni

Context
The mobile app must reach the backend from an emulator, a physical device, and a release APK.
Decision
EXPO_PUBLIC_API_URL is the single configuration point (emulator default 10.0.2.2, iOS simulator localhost, device/APK an explicit LAN or HTTPS URL). No in-app server-address UI.
Why
Configuration over product surface: a settings screen is UI the assignment never asked for, with validation, persistence, and UX costs — and a hosted deployment would just set an HTTPS URL through the same variable with no code change.
Alternatives
A runtime settings screen — considered during architecture and explicitly superseded by this policy.
Trade-off
Changing a built APK's API address requires a rebuild; the README documents the exact command.
Result
One documented variable covers every environment, and the release artifact's baked URL was verified in the built APK.
Bağlam
Mobil uygulamanın backend'e emülatörden, fiziksel bir cihazdan ve release APK'dan erişebilmesi gerekiyor.
Karar
EXPO_PUBLIC_API_URL tek yapılandırma noktası (emülatör varsayılanı 10.0.2.2, iOS simülatörü localhost, cihaz/APK için açıkça verilen bir LAN veya HTTPS URL'i). Uygulama içinde sunucu adresi UI'ı yok.
Gerekçe
Ürün yüzeyi yerine konfigürasyon: ayar ekranı, ödevin hiç istemediği; validasyon, kalıcılık ve UX maliyeti getiren bir UI olurdu — hosted bir deployment ise kod değişikliği olmadan aynı değişken üzerinden bir HTTPS URL'i verirdi.
Değerlendirilen alternatifler
Runtime bir ayar ekranı — mimari aşamasında değerlendirildi ve açıkça bu politikayla değiştirildi.
Trade-off
Build edilmiş bir APK'nın API adresini değiştirmek yeniden build gerektiriyor; README tam komutu belgeliyor.
Sonuç
Belgelenmiş tek bir değişken tüm ortamları kapsıyor ve release çıktısına gömülen URL, build edilen APK içinde doğrulandı.

11 · Lightweight EN/TR localization, English default, TRY everywhere

11 · Hafif EN/TR yerelleştirme, varsayılan İngilizce, her yerde TRY

Context
The domain data and every backend message are Turkish; the evaluation context is Turkish; the project decision was an English-default interface.
Decision
Both clients ship English (default) and Turkish via small typed message catalogs, switchable at runtime and persisted. API data is never translated. Prices are always TRY, formatted from integer kuruş.
Why
Two locales and a small message set don't justify an i18n framework or translation backend. Typed catalogs also make a missing translation a compile error.
Alternatives
i18next and similar — infrastructure disproportionate to two locales. Translating backend error prose by string-matching — brittle and forbidden: known failures are identified by status code plus request context instead, with a localized generic fallback otherwise.
Trade-off
Mixed-language screens are possible by design (English chrome around Turkish product names) — the honest outcome, since renaming API data would be worse.
Result
A full Turkish pass was verified in the release APK, including decimal-comma currency formatting.
Bağlam
Domain verisi ve tüm backend mesajları Türkçe; değerlendirme bağlamı Türkçe; proje kararı ise varsayılanı İngilizce olan bir arayüzdü.
Karar
Her iki istemci de küçük ve tipli mesaj kataloglarıyla İngilizce (varsayılan) ve Türkçe sunuyor; çalışma anında değiştirilebiliyor ve kalıcılaştırılıyor. API verisi hiçbir zaman çevrilmiyor. Fiyatlar her zaman TRY ve tam sayı kuruştan formatlanıyor.
Gerekçe
İki dil ve küçük bir mesaj kümesi, bir i18n framework'ünü veya çeviri backend'ini gerekçelendirmiyor. Tipli kataloglar ayrıca eksik bir çeviriyi derleme hatasına dönüştürüyor.
Değerlendirilen alternatifler
i18next ve benzerleri — iki dil için orantısız altyapı. Backend hata metinlerini string eşleştirmeyle çevirmek — kırılgan ve yasak: bilinen hatalar bunun yerine status kodu ve istek bağlamıyla tanınıyor, kalanlar için yerelleştirilmiş genel bir fallback mesajı kullanılıyor.
Trade-off
Tasarım gereği karışık dilli ekranlar mümkün (Türkçe ürün adlarının çevresinde İngilizce arayüz) — dürüst sonuç bu, çünkü API verisini yeniden adlandırmak daha kötü olurdu.
Sonuç
Release APK içinde uçtan uca Türkçe bir kullanım akışı doğrulandı; ondalık virgüllü para formatı dâhil.

12 · Modifying the provided backend — three times, minimally

12 · Verilen backend'i değiştirmek — üç kez, asgari düzeyde

Context
The assignment says to avoid backend changes, but its own mandatory requirements collided with the provided API in one place, and two product rules were judged to belong server-side.
Decision
Add GET /products/{id}; reject stock updates on Discontinued products with 409; rate-limit product reads. Nothing else.
Why
The detail endpoint closes a proven silent-data-loss trap in the full-replace PUT. The 409 protects against stale clients in a way a disabled button cannot. The rate limit is the independent boundary that client-side refresh cooldowns are not.
Alternatives
For the detail endpoint: guessing the missing fields client-side, widening the list DTO, or relaxing PUT semantics — all rejected as either data-corrupting or more invasive. Full detail per modification: backend report.
Trade-off
Any backend change is a deviation from the assignment's preference; each was kept to a controller action, a guard, or a middleware policy, following existing patterns and error conventions.
Result
Every modification is documented in the API contract with runtime verification, and no existing endpoint's behavior changed.
Bağlam
Ödev backend değişikliklerinden kaçınılmasını söylüyor, ama kendi zorunlu gereksinimleri bir noktada verilen API ile çakıştı ve iki ürün kuralının sunucu tarafına ait olduğuna karar verildi.
Karar
GET /products/{id} eklendi; Discontinued ürünlerdeki stok güncellemeleri 409 ile reddediliyor; ürün okumalarına rate limit uygulanıyor. Başka bir şey yok.
Gerekçe
Detay endpoint'i, full-replace PUT'taki kanıtlanmış sessiz veri kaybı tuzağını kapatıyor. 409, devre dışı bırakılmış bir butonun sağlayamayacağı biçimde stale istemcilere karşı koruma sağlıyor. Rate limit ise istemci tarafındaki refresh cooldown'larının olamadığı bağımsız sınır.
Değerlendirilen alternatifler
Detay endpoint'i için: eksik alanları istemci tarafında tahmin etmek, liste DTO'sunu genişletmek veya PUT semantiğini gevşetmek — hepsi ya veriyi bozduğu ya da daha müdahaleci olduğu için reddedildi. Her değişikliğin tüm ayrıntısı: backend raporu.
Trade-off
Her backend değişikliği ödevin tercihinden bir sapmadır; her biri mevcut kalıplara ve hata konvansiyonlarına uyularak bir controller action'ı, bir guard veya bir middleware politikasıyla sınırlı tutuldu.
Sonuç
Her değişiklik API kontratında runtime doğrulamasıyla belgelendi ve mevcut hiçbir endpoint'in davranışı değişmedi.

13 · One refresh pipeline per dataset, with layered protection

13 · Veri kümesi başına tek refresh hattı, katmanlı korumayla

Context
Multiple clients edit the same catalog, and the optional bonus asks the open web list to reflect other clients' changes. Manual buttons, pull-to-refresh, lifecycle revalidation, background polls, and web mutation invalidation can trigger reads; mobile stock success instead patches caches without refetching.
Decision
The visible/focused web list polls its exact current query about every 15 s. Mobile polls only the current detail about every 10 s while that screen is focused and the app is active; refocus/foreground revalidates that detail. Polls are anchored to the last fetch settle, joined refetches reuse the in-flight request, manual refresh has a ~4 s cooldown, 4xx is never auto-retried, and the three product GETs share an independent 60/10 s rate limit per authorization value (IP fallback). Freshness is displayed from the last successful fetch.
Why
Refreshing should raise confidence in the data without disrupting work or creating avoidable load. Anchoring means a manual or lifecycle refetch pushes the next automatic one a full interval out. A cache-only mobile stock success does not perform a read or reset the scheduler.
Alternatives
WebSockets/SSE/SignalR — realtime infrastructure plus backend changes the assignment discourages. A plain refetchInterval — simpler, but it free-runs and stacks on top of other triggers.
Trade-off
Convergence is bounded by the poll interval (~15 s on the web list, ~10 s on the focused mobile detail) rather than instant.
Result
Verified on both clients: an external stock change made with curl appears through the refresh pipeline, with the cooldown visibly protecting the button.
Bağlam
Aynı kataloğu birden fazla istemci düzenliyor ve isteğe bağlı bonus, açık duran web listesinin diğer istemcilerin değişikliklerini yansıtmasını istiyor. Manuel butonlar, pull-to-refresh, yaşam döngüsü revalidation'ı, arka plan polling'i ve web mutation invalidation'ı okuma tetikleyebilir; mobil stok başarısı ise refetch yapmadan cache'leri yamalar.
Karar
Görünür/odaktaki web listesi, açık query'sini tam parametreleriyle yaklaşık 15 saniyede bir poll eder. Mobil, yalnızca açık detayı — ekran odaktayken ve uygulama aktifken — yaklaşık 10 saniyede bir poll eder; odağa/ön plana dönüş o detayı yeniden doğrular. Polling son fetch'in bitişine hizalanır, aynı ana denk gelen refetch'ler devam eden isteği paylaşır, manuel refresh'in ~4 saniyelik cooldown'u vardır, 4xx asla otomatik denenmez ve üç ürün GET'i authorization değeri başına (fallback: IP) bağımsız 60/10 saniyelik rate limit'i paylaşır. Tazelik, son başarılı fetch'ten gösterilir.
Gerekçe
Yenileme, işi bölmeden ve önlenebilir yük yaratmadan veriye duyulan güveni artırmalı. Hizalama, manuel veya yaşam döngüsü kaynaklı bir refetch'in bir sonraki otomatik fetch'i tam bir aralık ileri itmesi demek. Yalnızca cache'i yamalayan mobil stok başarısı, okuma yapmaz ve zamanlayıcıyı sıfırlamaz.
Değerlendirilen alternatifler
WebSocket/SSE/SignalR — realtime altyapı ve ödevin önermediği backend değişiklikleri. Düz bir refetchInterval — daha basit, ama serbest çalışıyor ve diğer tetikleyicilerin üzerine biniyor.
Trade-off
Tutarlılığa ulaşma anlık değil, polling aralığıyla sınırlı (web listesinde ~15 saniye, odaktaki mobil detayda ~10 saniye).
Sonuç
Her iki istemcide doğrulandı: curl ile dışarıdan yapılan bir stok değişikliği refresh hattı üzerinden görünüyor ve cooldown, butonu gözle görülür biçimde koruyor.

14 · Accepting last-write-wins instead of faking safety

14 · Sahte güvenlik üretmek yerine last-write-wins'i kabul etmek

Context
Discovery verified exhaustively that the backend has no concurrency protection: no versions, no ETag/If-Match (stale preconditions are ignored and return 200), no 412 path. Lost updates were reproduced at runtime.
Decision
Accept it. Build no client-side concurrency protocol. Mitigate at UX level only: edit forms initialize from a fresh read, every mutation applies the server's returned state, the mobile stock editor surfaces "changed elsewhere" instead of silently overwriting a dirty draft, and the limitation is documented.
Why
Any client-side "protection" would be safety the server does not enforce — and inventing API behavior was explicitly out of bounds.
Alternatives
Emulating If-Match or updatedAt preconditions client-side — rejected as fake safety. Adding a version column to the backend — a substantially more invasive change than the three that were made.
Trade-off
Simultaneous edits can still overwrite each other; the user is never misled into thinking otherwise.
Result
The one place where a domain rule can protect a stale client — discontinued products — is enforced server-side, and is documented as a domain rejection rather than a version check.
Bağlam
Keşif aşaması, backend'de concurrency koruması bulunmadığını ayrıntılı biçimde doğruladı: versiyon alanı yok, ETag/If-Match yok (stale precondition'lar yok sayılıp 200 dönüyor), 412 yolu yok. Kayıp güncellemeler runtime'da yeniden üretildi.
Karar
Bunu kabul et. İstemci tarafında bir concurrency protokolü kurma. Yalnızca UX düzeyinde hafiflet: düzenleme formları taze bir okumadan başlatılıyor, her mutation sunucunun döndürdüğü state'i uyguluyor, mobil stok editörü kirli bir taslağı sessizce ezmek yerine "başka yerde değişti" uyarısını gösteriyor ve kısıt belgeleniyor.
Gerekçe
İstemci tarafındaki herhangi bir "koruma", sunucunun uygulamadığı bir güvenlik olurdu — API davranışı uydurmak ise açıkça kapsam dışıydı.
Değerlendirilen alternatifler
If-Match veya updatedAt precondition'larını istemci tarafında taklit etmek — sahte güvenlik olarak reddedildi. Backend'e bir versiyon kolonu eklemek — yapılan üç değişiklikten belirgin biçimde daha müdahaleci bir değişiklik.
Trade-off
Eşzamanlı düzenlemeler hâlâ birbirini ezebilir; kullanıcı aksini düşünecek şekilde asla yanıltılmıyor.
Sonuç
Bir domain kuralının stale bir istemciyi koruyabildiği tek yer — Discontinued ürünler — sunucu tarafında uygulanıyor ve bir versiyon kontrolü olarak değil, domain reddi olarak belgeleniyor.
