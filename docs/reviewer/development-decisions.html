Engineering decisions

Why the delivered solution is built the way it is. Each entry gives the context, the decision, the reasoning, the alternatives that were actually considered, the trade-off accepted, and the result. This is a decision record, not a chronology.

1 · One repository, npm workspaces

Context
Two clients that must agree exactly on types and API behavior, plus the provided backend, delivered as one submission.
Decision
A flat npm-workspaces monorepo: shared, web, mobile, with the backend alongside. shared ships TypeScript source directly — no build step, no project references.
Why
One install, one dependency tree, one lockfile. npm ships with Node, so a reviewer needs no extra tooling, and it has the fewest React Native/Metro edge cases. Vite transpiles workspace TypeScript and Metro compiles through Babel, so source-only sharing just works.
Alternatives
pnpm — faster, but adds an install step for the reviewer and occasional Metro friction whose standard mitigation reproduces npm's layout anyway. Separate folders without workspaces — duplicated types and client code. Nx/Turborepo — a build graph for three packages.
Trade-off
npm's flat node_modules is less strict about phantom dependencies than pnpm's isolated layout.
Result
A reviewer runs npm install once at the root and everything works, including the mobile build.

2 · Share the wire, not the UI

Context
Two clients, one API with several verified traps (full-replace PUT, plain-text errors, strict token rotation).
Decision
Share only framework-free code whose behavior is genuinely identical on both platforms: API/domain types, the fetch client core, the query-key factory, and small formatting/normalization utilities. UI, navigation, forms, and storage stay per-app; each app injects its own storage adapter.
Why
The plumbing that must be exactly right — error normalization, Bearer injection, refresh-and-retry — is implemented once and gets one set of tests. Query keys are shared so cache and invalidation semantics can't drift between clients.
Alternatives
A shared UI component package — rejected: DOM and React Native primitives don't share cleanly at this scale and the result is lowest-common-denominator components. Duplicating the client per app — two places to get token rotation wrong.
Trade-off
A little indirection: platform behavior enters through injected adapters rather than being inline.
Result
Roughly 500 lines of shared source carry every cross-client correctness concern, covered by unit tests plus live contract tests against the running backend.

3 · TanStack Query as the only server-state layer

Context
Almost all application state in this product is server state. (Using TanStack Query was a fixed project decision; it was adopted willingly.)
Decision
TanStack Query v5 on both clients, with no additional state library. Remaining client state is one auth context plus local component state.
Why
Query keys per filter combination give stale-response protection for free — a late response lands under its own key and can never overwrite the current view. keepPreviousData delivers the required "keep results visible while loading" behavior natively, and invalidation delivers "the list shows persisted state after an update".
Alternatives
Redux/Zustand/Jotai on top — would duplicate a cache that already exists. Hand-rolled fetching hooks — reimplements deduplication, caching, and revalidation badly.
Trade-off
No optimistic updates by design: the UX contract requires showing persisted server state after a save, so optimism would add rollback complexity for no required behavior.
Result
No global store exists in either client, and none is missing.

4 · Centralized, single-flight 401 → refresh → retry

Context
Verified backend behavior: 15-minute access tokens; refresh tokens rotate strictly (replaying one kills the session); logout on one client invalidates the other's access tokens immediately; a backend restart wipes every session.
Decision
One interceptor in the shared client: on 401, refresh once behind a mutex, persist the new pair before resolving, retry the original request exactly once. Refresh failure clears storage and returns the app to login. A session-epoch counter invalidates in-flight handling across login/logout boundaries.
Why
This is required plumbing, not an enhancement — without it both apps appear randomly broken mid-use. Rotation makes concurrent refreshes fatal, so single-flight is a correctness requirement, not an optimization.
Alternatives
Proactive expiry timers — clock-skew and lifecycle complexity for no benefit over reactive refresh. Per-app implementations — two chances to get rotation wrong. Shared token storage between clients — each client legitimately owns its own session chain.
Trade-off
The first request after expiry pays one extra round trip.
Result
Session-expiry, cross-client-logout, and backend-restart recovery were all exercised end-to-end, including in the release APK.

5 · The web list state lives in the URL

Context
The admin list carries search, three filters, sort, direction, and page — and the UX requires that returning from a product detail preserves all of it.
Decision
All of it lives in URL search params; the parsed params are the TanStack query key.
Why
"Preserve the view" comes for free from the browser's own history, and it survives reload, is shareable, and makes the displayed data and the address bar structurally incapable of disagreeing.
Alternatives
Component state plus a restoration mechanism — more code and a new class of bug (state and URL drifting apart).
Trade-off
Search input needs a 300 ms debounce before it reaches the URL, so typing doesn't spam history.
Result
Filter/sort/page state is inspectable in the address bar during review — e.g. ?status=3&sort=price&dir=desc.

6 · shadcn/ui on Tailwind for the web admin

Context
An operational admin UI needing accessible primitives — table, select, dialog, toast — without adopting a design system.
Decision
shadcn/ui components vendored into the repository on Tailwind CSS v4; only the ~10 components the assignment needs.
Why
The components are owned source in the repo: inspectable, adaptable, and reviewable, with accessible Radix primitives underneath and a small dependency surface.
Alternatives
Mantine — a strong fit for the table/snackbar requirements (and the initial discovery recommendation), but a larger opaque dependency with its own styling system. MUI — heavier still. Hand-rolled CSS — the weakest accessibility for the effort.
Trade-off
Vendored components are code to maintain; the mitigation is composing rather than modifying primitives, with domain display logic kept in one place.
Result
A consistent admin surface that never grew into a design-system project.

7 · Hand-styled mobile UI, no component kit

Context
Four mobile screens plus feedback states, with queued bottom snackbars required by the UX decisions.
Decision
React Native StyleSheet with a small owned primitive set and a token file; no RN Paper or equivalent.
Why
The genuinely hard piece — a queued snackbar system — needs custom code even with a kit (Paper's is single-instance), so a kit would have added a dependency without removing work. It also keeps the mobile look free of a third-party visual identity.
Alternatives
React Native Paper — kept as an explicit escape hatch if velocity had suffered; it wasn't needed.
Trade-off
More styling effort, accepted for a minimal dependency set.
Result
A coherent surface system (documented in mobile/DESIGN.md) with two UI-related runtime dependencies: navigation and safe-area handling.

8 · Deliberately different designs for admin and mobile

Context
One product family, two audiences: head-office operators at a desk and store staff on a phone.
Decision
Share the data language — status semantics, stock thresholds, currency formatting, terminology — but not the visual system. Web is a dense operational table; mobile is a productized browsing-and-editing surface.
Why
Operators scan many rows and compare values; store staff hold a phone one-handed and act on one product. Forcing one visual system on both would compromise the primary task of each.
Alternatives
A shared component/design package — rejected for the same reason as shared UI code generally.
Trade-off
Two style systems to keep coherent; mitigated by recording both in DESIGN.md files so later passes extend rather than reinvent them.
Result
Each surface reads as fit for its user, while status colours and ₺ amounts mean the same thing everywhere.

9 · Expo managed workflow, APK built locally with Gradle

Context
The assignment requires a working Android APK; Expo vs bare React Native was left open.
Decision
Expo managed workflow; the deliverable APK produced by expo prebuild + local gradlew assembleRelease, signed with the Gradle debug keystore and documented as assignment-grade.
Why
No cloud build account or queue; reproducible offline; the reviewer can run the exact same documented commands. Managed Expo keeps native configuration declarative — including the cleartext-HTTP flag the HTTP-only backend requires — while prebuild yields the full native project when Gradle needs it.
Alternatives
EAS cloud build — an account and upload dependency for the reviewer's reproduction path. Bare React Native — permanent native-config maintenance in exchange for one-time prebuild output.
Trade-off
Debug-keystore signing is not store-ready, and the first Gradle build is slow and network-heavy.
Result
The delivered APK was built from a known commit and verified standalone on an emulator against the live backend — an APK that merely builds was explicitly not treated as done.

10 · One environment variable instead of a server-settings screen

Context
The mobile app must reach the backend from an emulator, a physical device, and a release APK.
Decision
EXPO_PUBLIC_API_URL is the single configuration point (emulator default 10.0.2.2, iOS simulator localhost, device/APK an explicit LAN or HTTPS URL). No in-app server-address UI.
Why
Configuration over product surface: a settings screen is UI the assignment never asked for, with validation, persistence, and UX costs — and a hosted deployment would just set an HTTPS URL through the same variable with no code change.
Alternatives
A runtime settings screen — considered during architecture and explicitly superseded by this policy.
Trade-off
Changing a built APK's API address requires a rebuild; the README documents the exact command.
Result
One documented variable covers every environment, and the release artifact's baked URL was verified in the built APK.

11 · Lightweight EN/TR localization, English default, TRY everywhere

Context
The domain data and every backend message are Turkish; the evaluation context is Turkish; the project decision was an English-default interface.
Decision
Both clients ship English (default) and Turkish via small typed message catalogs, switchable at runtime and persisted. API data is never translated. Prices are always TRY, formatted from integer kuruş.
Why
Two locales and a small message set don't justify an i18n framework or translation backend. Typed catalogs also make a missing translation a compile error.
Alternatives
i18next and similar — infrastructure disproportionate to two locales. Translating backend error prose by string-matching — brittle and forbidden: known failures are identified by status code plus request context instead, with a localized generic fallback otherwise.
Trade-off
Mixed-language screens are possible by design (English chrome around Turkish product names) — the honest outcome, since renaming API data would be worse.
Result
A full Turkish pass was verified in the release APK, including decimal-comma currency formatting.

12 · Modifying the provided backend — three times, minimally

Context
The assignment says to avoid backend changes, but its own mandatory requirements collided with the provided API in one place, and two product rules were judged to belong server-side.
Decision
Add GET /products/{id}; reject stock updates on Discontinued products with 409; rate-limit product reads. Nothing else.
Why
The detail endpoint closes a proven silent-data-loss trap in the full-replace PUT. The 409 protects against stale clients in a way a disabled button cannot. The rate limit is the independent boundary that client-side refresh cooldowns are not.
Alternatives
For the detail endpoint: guessing the missing fields client-side, widening the list DTO, or relaxing PUT semantics — all rejected as either data-corrupting or more invasive. Full detail per modification: backend report.
Trade-off
Any backend change is a deviation from the assignment's preference; each was kept to a controller action, a guard, or a middleware policy, following existing patterns and error conventions.
Result
Every modification is documented in the API contract with runtime verification, and no existing endpoint's behavior changed.

13 · One refresh pipeline per dataset, with layered protection

Context
Multiple clients edit the same catalog, and the optional bonus asks the open web list to reflect other clients' changes. Several mechanisms can trigger a refetch: manual buttons, pull-to-refresh, focus/reconnect revalidation, mutation invalidation, and background polls.
Decision
Every trigger converges on one TanStack query fetch per key. Background polls are anchored to the last fetch settle rather than running on a free interval, joined refetches reuse the in-flight request, manual refresh has a ~4 s cooldown, 4xx is never auto-retried, and the backend rate-limits reads independently. Freshness is displayed from the last successful fetch.
Why
Refreshing should raise confidence in the data without disrupting work or creating avoidable load. Anchoring the poll means a manual or mutation-driven refetch pushes the next automatic one a full interval out, so triggers can never stack.
Alternatives
WebSockets/SSE/SignalR — realtime infrastructure plus backend changes the assignment discourages. A plain refetchInterval — simpler, but it free-runs and stacks on top of other triggers.
Trade-off
Convergence is bounded by the poll interval (~15 s on the web list) rather than instant.
Result
Verified on both clients: an external stock change made with curl appears through the refresh pipeline, with the cooldown visibly protecting the button.

14 · Accepting last-write-wins instead of faking safety

Context
Discovery verified exhaustively that the backend has no concurrency protection: no versions, no ETag/If-Match (stale preconditions are ignored and return 200), no 412 path. Lost updates were reproduced at runtime.
Decision
Accept it. Build no client-side concurrency protocol. Mitigate at UX level only: edit forms initialize from a fresh read, every mutation applies the server's returned state, the mobile stock editor surfaces "changed elsewhere" instead of silently overwriting a dirty draft, and the limitation is documented.
Why
Any client-side "protection" would be safety the server does not enforce — and inventing API behavior was explicitly out of bounds.
Alternatives
Emulating If-Match or updatedAt preconditions client-side — rejected as fake safety. Adding a version column to the backend — a substantially more invasive change than the three that were made.
Trade-off
Simultaneous edits can still overwrite each other; the user is never misled into thinking otherwise.
Result
The one place where a domain rule can protect a stale client — discontinued products — is enforced server-side, and is documented as a domain rejection rather than a version check.
