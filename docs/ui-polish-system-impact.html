Agentic UI Polish System — Impact Report

What this change adds, what it touches, what it deliberately does not touch, and how to use and undo it. Branch fm/ui-polish-system · 2026-08-31.

1 · Executive summary

This PR introduces a repeatable, documented UI-polish workflow for Claude Code into the StokMate repository. It combines Anthropic's official frontend-design skill (general design judgment) with a repository-specific product-ui-polish skill (product constraints, inspection workflow, implementation discipline, verification), persistent design documentation (DESIGN.md at root, web/, and mobile/), and project-scoped inspection tooling (Chrome DevTools MCP for the rendered web app, the shadcn registry MCP, and the already-present official Expo plugin for mobile).

Zero product change. This PR adds tooling, configuration, and documentation only. No product screen, style, component, API, or behavior was modified. The full verification suite (typecheck, lint, tests, production web build) passes unchanged.

End state: a future session can be asked /product-ui-polish products web table and Claude will inspect the real rendered UI, critique it against StokMate's recorded design language, implement the smallest coherent improvement, and verify the result visually and behaviorally.

2 · Architecture

Division of labor: frontend-design brings general visual judgment (typography, hierarchy, restraint, self-critique). product-ui-polish overrides its "distinctive identity / aesthetic risk" framing with StokMate's operational-software rules, and adds everything the official skill cannot know: the recorded design language, the approved UX decisions, the inspection tooling, and the verification bar.

8 · Future workflow (how a polish pass runs)

/product-ui-polish products web table
  1. Understand: the target is the admin product table — head-office operators scanning/comparing inventory; primary info per UX-006 hierarchy.
  2. Context: read root + web/DESIGN.md, docs/UX_DECISIONS.md, references/admin.md + data-tables.md.
  3. Inspect: start backend + npm run dev:web; use the Chrome DevTools MCP to screenshot the table at ~1440 / 768 / 375 px, in loading, loaded, filtered, empty, and error states, EN and TR.
  4. Diagnose: written critique separating usability problems from aesthetic preference, ranked comprehension-first.
  5. References (optional): a few shadcn registry table patterns as anatomy reference — never a template.
  6. Implement: smallest coherent change with existing tokens/components.
  7. Verify: same screenshots re-taken and compared ("clearly better" or revise); keyboard/responsive/state behavior re-checked; typecheck/lint/build:web run.
  8. Record: any new convention written back into the relevant DESIGN.md.

Mobile targets run the same loop against the Android emulator dev build (Metro 8082, quick facts in AGENTS.md) with Expo tooling and adb screenshots.

9 · Admin design rules (summary)

Operational software for long sessions: useful density, repeated-use optimization, minimal cognitive load, scanability, recognition over recall, progressive disclosure, preserved context, error prevention, clear feedback. Avoid both dated-enterprise and artistic-SaaS styling — no giant type, decorative dashboards, card nesting, gradients, glassmorphism, glow, heavy shadows, badge excess. Polish comes from precision: spacing rhythm, alignment, type scale, component anatomy, complete interaction states, cross-screen consistency. Full text: references/admin.md, references/data-tables.md, references/data-visualization.md.

10 · Mobile design rules (summary)

Touch-first for store staff, not a compressed admin: shortest path to find-product-and-update-stock, one-handed reach, ≥44pt targets with press feedback, shallow navigation, name+stock-first hierarchy, immediate feedback, safe areas and keyboard correctness. Same product family as the admin — share color semantics, terminology, status language, ₺ formatting, interaction tone; adapt density, navigation, anatomy, type scale, layout. Full text: references/mobile.md.

11 · Data freshness policy (summary)

Server-backed screens may show "Updated n ago · Refresh" (customer-calm wording — never "Hard refresh"). The timestamp is the last successful fetch; failures never advance it. Manual refresh revalidates through TanStack Query, preserving search/filters/sort/pagination/scroll, keeping data visible while loading. All refresh sources (button, pull-to-refresh, focus, reconnect, polling, invalidation) coordinate into one in-flight request with dedup, short cooldown, bounded backoff retries; client throttling is UX, not a security boundary — expensive endpoints need backend rate limiting. Full text: references/data-freshness.md. A parallel product PR may implement freshness UI; the reference documents the pattern and defers to the shipped implementation.

12 · Context / token implications

  • Always loaded: only the skill's name + one-line description (skill listing) and the single new AGENTS.md bullet. A few hundred tokens.
  • Loaded on invocation: SKILL.md (~1.3k words) plus only the relevant reference file(s). DESIGN.md files are read on demand during step B.
  • MCP servers: tool schemas load per session where supported on demand; the chrome-devtools toolset is the largest single addition when actually used.
  • frontend-design: a skill in the official plugin; loads when design work triggers it, not on every prompt.

13 · Security / privacy implications

  • No secrets committed. Nothing in this PR contains or requires a credential. The only credentialed option (21st.dev) was documented, not configured.
  • Chrome DevTools MCP exposes the controlled browser's content to the agent (upstream's own warning). Usage here targets localhost dev servers with seeded test data; avoid pointing it at sessions containing personal data.
  • shadcn MCP talks to the public shadcn registry; no source code leaves the machine beyond ordinary registry queries.
  • Expo MCP (pre-existing) is a remote server with optional account sign-in via /mcp; no credentials stored in the repo.
  • MCP servers and plugins run with developer-level local permissions — the standard Claude Code per-project trust prompts remain the gate.

16 · Rollback

The system is additive; removal is one revert of the PR's commit(s):

git revert <merge-commit-sha>   # or: git revert <commit-sha>

Manual equivalent: delete .mcp.json, .claude/settings.json, .claude/skills/product-ui-polish/, DESIGN.md, web/DESIGN.md, mobile/DESIGN.md, docs/ui-polish-system-impact.html, and remove the one added bullet in AGENTS.md. Nothing else references these files; no state is left behind (any plugin caches live outside the repo and expire harmlessly).
